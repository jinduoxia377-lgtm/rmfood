# DS Bot 群聊功能深度核查报告

> 核查时间：2026-10-13 深夜
> 核查范围：群聊协作 + v2 自主派单的**结构性问题**与**功能性问题**
> 方法：代码级核查（前端组件/后端服务/数据流）+ 既有 HTTP 实测结论复核

---

## 一、严重结构性问题

### S1. 动态创建的临时专家在前端不可见（功能影响大，确定存在）
- **现象**：自主派单 L2 动态创建的临时专家（如"毒理专家"）出现在群聊消息 `sender_bot_id` 中，但前端 `bots` 列表**不包含**该 Bot。
- **根因**：
  - `AgentPage.loadBots` 只在页面挂载时加载一次；群聊视图（`GroupChatPanel`）不触发刷新。
  - `GroupChatView` 的 `botName()` / `botAvatar()` / 成员管理全部用 `bots.find(b => b.id === botId)` 查名字，查不到就显示 `Bot#<id>`。
- **后果**：
  - 临时专家的消息发送者显示为 `Bot#9`（而非"毒理专家"）；
  - 成员管理对话框无法正确显示临时专家；
  - 用户无法在群聊中"看到"系统自动创建的专家。
- **修复方向**：① `GroupChatView` 增加"动态 bot 信息缓存"——遇到未知 `sender_bot_id` 时调用 `botApi.get(id)` 拉取并缓存；② 或 `AgentPage` 在进入群聊视图时刷新 `bots`；③ 更彻底：后端在群聊消息中冗余 `sender_bot_name` 字段。

### S2. 自主派单缺少【派单计划】消息（与方案文档 v2 4.1 不符）
- **现象**：实测消息流只有 `⏳ Chief 正在组织团队… → 各专家结果 → 【汇总】`，**没有独立的【派单计划】**。
- **根因**：Chief 的 system prompt 要求"第一步输出【派单计划】"，但 orchestrator `execute_smart` 在 LLM 第一步**只输出文本（无 tool_calls）时立即结束循环**（`if not tool_calls: break`），不会"先计划再继续派单"。
- **后果**：用户看不到任务被拆成了哪几个子任务、分别派给谁；可观测性承诺未兑现。
- **修复方向**：
  - 方案 A（推荐）：在 `_run_chief_dispatch` 后台任务开始时，用**一次轻量 LLM 调用**生成计划 JSON（子任务清单），并写一条群聊消息【派单计划】；
  - 方案 B：修改 orchestrator，允许 LLM 在循环中输出文本后继续（复杂度高，易失控）。

### S3. 群聊级互斥锁与频率限制为进程内存态
- `_GROUP_LOCKS` 与 `_LAST_DISPATCH_AT` 是**模块级内存 dict**。
- **后果**：多 uvicorn worker / 多实例部署时锁失效（每进程独立），频率限制失效；进程重启后重置。
- **修复方向**：单实例可接受；生产环境需迁移 Redis（`inference_queue`/Redis 锁）。**当前应至少在文档标注"仅支持单实例部署"**。

### S4. 后台自主派单任务无持久化与恢复
- `asyncio.create_task` 创建的后台任务无任务表；进程重启 / worker 回收会导致进行中的派单中断（已写入的计划/部分结果保留，但**不会有【汇总】**）。
- **修复方向**（增强）：新增 `ai_bot_tasks` 表（group_id, status, plan, results, created_at），启动时扫描未完成任务并恢复；或用 Celery/ARQ 等任务队列。

### S5. 临时专家长期积累导致团队膨胀
- 每次派单最多创建 2 个临时专家，无自动归档；用户 Bot 列表会累积大量"XX专家"。
- **修复方向**：临时专家标记 `is_auto_created=true`（新字段）或通过 `description` 标记；提供"自动归档 7 天后"策略或一键清理入口。

## 二、严重功能性问题

### F1. 引用消息不显示被引用内容
- `reply_to` 已存储，但前端消息渲染**不展示被引用消息内容**；用户看不到"引用了什么"。
- **修复方向**：在消息上方渲染引用块（含被引用消息内容，点击可定位）。

### F2. L3 兜底的诚实标注不强制
- delegate 在 L2 创建上限/失败时返回 `success=False`，Chief 看到后自行处理，但**结果不一定标注"超出平台专业工具，以下为通用分析"**。
- **修复方向**：`_run_chief_dispatch` 检测到 delegate 返回失败时，在最终汇总前自动给相关子任务结果加"（通用分析，超出平台专业工具）"前缀。

### F3. `mentioned_bot_ids` 未校验必须是群成员
- 后端 `post_message` 不校验 `mentioned_bot_ids` 是否为该群成员；任意 bot_id 可被 @。
- **修复方向**：在 `post_message` 中过滤为群成员集合（非成员忽略或 400）。

### F4. 自主派单期间输入被禁用（体验）
- `sending` 在异步派单期间一直为 `true`，按钮/输入禁用数分钟。
- **修复方向**：改为"发送请求中禁用"（请求返回后即恢复），派单进行中允许继续输入（后端会返回"进行中"提示）。

## 三、轻微问题

1. **`seenIdsRef` 切换群聊时未清空**：`useEffect [group]` 只 `setMessages([])`，未 `seenIdsRef.current = new Set()`；因消息 id 全局唯一，实际不误过滤，但不干净。
2. **delegate `created` 标记不精确**：`result.data["created"]` 用 `bool(context.get("_l2_created_count"))` 判断，累计值 >0 即 true（首次和后续 L2 都标 true）。
3. **后台长任务可能超 session 空闲**：`context["db"]` 是独立会话，极长派单（>session idle timeout）可能失效；当前场景（分钟级）可接受。

## 四、问题优先级建议

| 级别 | 问题 | 建议处理 |
|:---:|:---|:---|
| P0（功能正确性） | S1 临时专家前端不可见 | 本次应修复 |
| P0 | S2 缺少【派单计划】消息 | 本次应修复 |
| P1（体验/安全） | F1 引用不显示内容 | 本次可修复 |
| P1 | F2 L3 标注不强制 | 本次可修复 |
| P1 | F3 @ 未校验群成员 | 本次可修复 |
| P2（架构） | S3/S4/S5、F4、轻微项 | 建议记录为后续演进项（Redis、任务表、归档） |

---

## 五、结论

群聊核心链路（创建/发言/自主派单/异步轮询/消息流）**功能可用**，但存在 **2 个 P0 功能正确性问题**（临时专家前端不可见、缺少派单计划）和 **3 个 P1 体验/安全问题**。建议优先修复 P0/P1，再进入第三阶段。

## 六、最终核查补充（2026-10-14 深夜）

对 v3.4（GitHub 自动供给 + 任务驱动自动建群）全链路最终核查后，确认已修复的问题包括：
- `@dataclass` 装饰器、`NoneType` 输出、McpBridge 相对 URL/.env 路径、GitHub MCP 端点认证、
  TaskCenter 状态轮询、GitHub 供给（persona 校验/查重/多仓库）、LLM 瞬时失败重试、重复 tool_calls 检测。

**仍存在的设计缺口（尚未修复）：**

| 级别 | 问题 | 说明 |
|:---:|:---|:---|
| P0 | **自动建群阶段无 GitHub 供给** | `TaskTeamService` 配人时 L3 直接用通用临时专家兜底，**不会在创建任务阶段从 GitHub 获取专家**；GitHub 供给只在 Chief 派单的 delegate 中出现。与"建群配齐人员"的核心期望有差距 |
| P0 | **任务失败原因未在前端展示** | 任务卡片只显示"失败"徽标，不展示 `error_message`，用户无法知道失败原因 |
| P0 | **运行中超时任务无定时恢复** | `recover_stale_tasks` 只在服务启动时执行一次；运行中卡住的任务（如后台异常）不会自动标记 failed |
| P1 | **"追加专家"功能未实现** | v3.3 方案承诺任务详情可追加专家，前端 TaskCenter 未实现 |
| P1 | **群聊成员管理临时专家显示 Bot#id** | 成员管理对话框仍用 `bots.find`，未利用 `sender_bot_name` |
| P1 | **GitHub 登记的 MCP 服务器无启用通知** | `register_mcp_from_github` 生成的配置默认 disabled，用户不知晓可启用 |

**建议**：先修复 3 个 P0（建群阶段 GitHub 供给、前端失败原因展示、定时恢复），再视需要补 P1。
