# ADR-005: 基于 OpenTelemetry 的可观测性体系

## 状态
✅ 已接受 (2026-06-05)

## 上下文

当前系统拥有基础的请求日志（`RequestLoggingMiddleware`）和健康检查端点（`/health`），但缺乏：
1. **分布式追踪**：跨模块的请求链路无法串联（如：Web → API → AI → DB）
2. **指标聚合**：无法监控 API 延迟分布、错误率、QPS 等
3. **告警机制**：无主动告警，问题发现依赖人工
4. **日志结构化**：现有日志为自由文本，无法进行结构化分析
5. **SLA 验证**：无法量化验证可用性和性能承诺

## 决策

采用 **OpenTelemetry** 作为统一的可观测性标准，基于 **开源三件套** 构建：

```
┌─────────────────────────────────────────────────────────────┐
│                    可观测性体系架构                           │
│                                                              │
│  应用层                    存储层              可视化层       │
│  ┌─────────┐            ┌──────────┐        ┌──────────┐    │
│  │ Traces  │ ───OTLP──→ │ Tempo    │ ────→  │ Grafana  │    │
│  │ (FastAPI│            │ (追踪)   │        │ (统一仪表 │    │
│  │  + AI)  │            └──────────┘        │  盘)     │    │
│  ├─────────┤            ┌──────────┐        └──────────┘    │
│  │ Metrics │ ───OTLP──→ │ Prometheus│                          │
│  │ (业务指 │            │ (指标)   │                          │
│  │ 标)     │            └──────────┘                          │
│  ├─────────┤            ┌──────────┐                          │
│  │ Logs    │ ───OTLP──→ │ Loki     │                          │
│  │ (结构   │            │ (日志)   │                          │
│  │ 化日志) │            └──────────┘                          │
│  └─────────┘                                                 │
└─────────────────────────────────────────────────────────────┘
```

### 关键指标定义（RED 方法论）

| 指标 | 类型 | 采集方式 | 目标 |
|:-----|:-----|:---------|:----|
| **请求速率** | Rate | API 入口计数器 | — |
| **错误率** | Error | HTTP 5xx / 业务异常 | <1% |
| **延迟 P50/P95/P99** | Duration | 中间件埋点 | P99 <200ms |
| **数据库查询耗时** | Duration | SQLAlchemy Hook | P99 <50ms |
| **AI 推理延迟** | Duration | LLM Provider 包装器 | P95 <5s |
| **业务交易量** | Rate | 领域事件计数器 | — |
| **活跃用户数** | Gauge | WebSocket 连接数 | — |
| **缓存命中率** | Ratio | Cache Pipeline 日志 | >80% |

### 结构化日志格式

```python
# 所有日志采用统一 JSON 格式
{
    "timestamp": "2026-06-05T10:30:00.123Z",
    "level": "INFO",
    "trace_id": "abc123def456",
    "span_id": "span789",
    "service": "rmfood-backend",
    "module": "formula_service",
    "event": "formula.created",
    "user_id": "u_12345",
    "formula_id": "f_67890",
    "duration_ms": 145,
    "message": "配方创建成功"
}
```

### 告警规则（P0 级）

| 规则 | 条件 | 通知渠道 | 响应时间 |
|:-----|:-----|:---------|:--------:|
| API 错误率突增 | 5xx > 5%（5min） | 企业微信 + 短信 | 15min |
| 关键 API P99 超时 | P99 > 1s（5min） | 企业微信 | 30min |
| 数据库连接用尽 | 连接数 > 池 80% | 企业微信 | 30min |
| 服务宕机 | 健康检查连续失败 3 次 | 电话 | 10min |
| 缓存雪崩 | 缓存命中率 < 50% | 企业微信 | 60min |

## 后果

### 正面
- 全链路追踪：从浏览器请求到数据库查询的完整链路
- 主动告警：从"用户报修"到"系统自动通知"的转变
- 数据驱动优化：通过 Prometheus 指标持续优化性能

### 负面
- 引入 OpenTelemetry SDK 增加约 3-5% 的性能开销
- 维护 Grafana + Tempo + Loki + Prometheus 四个服务
- 初期需要约 2 周的基础设施搭建时间
