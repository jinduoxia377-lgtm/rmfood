# ADR-038: 语义化版本发布体系

> **状态**：✅ 已接受。**日期**：2026-10-25。**领域**：工程治理（版本管理 / 发布流程）
> **关联**：README「版本与代际地图」、「已知技术债务 P0」；ADR-007（数据库迁移与版本管理）、ADR-008（CI/CD）；CHANGELOG.md；`scripts/version/`

## 背景

项目成立 5 个月、累积 563 次提交与 46 篇 ADR，但**从未建立正式的版本号体系**。实测（2026-10-25）存在五处互相矛盾的版本口径：

| 位置 | 声明版本 | 问题 |
|:-----|:--------:|:-----|
| `package.json` / `frontend/package.json` / `miniprogram/package.json` | `1.0.0` | 三处初始默认值，从未 bump |
| `backend/pyproject.toml` | `2.0.0` | **后端已自行推进到 2.0.0**，前端却停在 1.0.0 |
| `backend/app/core/config.py` | `"1.0.0"` | 硬编码字面量，与 pyproject 不一致 |
| `.env.example` / `backend/.env.example` | `APP_VERSION=1.0.0` | **死配置**：`AppInfoConfig` 无 `alias`，环境变量从未流入运行时 |
| README badge + 正文 | `v2.0` / `v10.0` | 文档自述，无仓库实体支撑 |
| `git tag` | **0 个** | `git describe` 只能返回 commit hash，无任何可回滚锚点 |
| `CHANGELOG.md` | 不存在 | 变更历史散落在 ADR 与 commit message 中 |

直接后果：
1. **无法回滚**——没有 tag，生产事故只能靠 commit hash 反查；
2. **无法对外承诺**——下游集成方无法据版本号判断兼容性；
3. **运行时版本不可信**——`settings.app_version` 永远返回 `1.0.0`，而构建产物实际已是 2.0.0；
4. **无门禁**——版本号靠人工维护，必然漂移。

另发现一个关联缺陷：`register_version_routes()` 因 `'_IncludedRouter' object has no attribute 'path'`
抛异常，被 `main.py` 的 `try/except` 静默降级为 warning，导致 `/api`、`/api/v1/info`
**版本端点从未成功注册过**——即项目既无外部可见版本号，连暴露它的端点也一直是坏的。

## 决策

### 1. 确立「单一权威源 + 镜像同步」模型

平台发布版本以 **根 `package.json` 的 `version` 字段**为唯一权威源，其余 7 处为镜像：

| # | 文件 | 角色 | 解析规则 |
|:-:|:-----|:-----|:---------|
| 1 | `package.json` | **权威源** | JSON `.version` |
| 2 | `frontend/package.json` | Web 前端镜像 | JSON `.version` |
| 3 | `miniprogram/package.json` | 微信小程序镜像 | JSON `.version` |
| 4 | `backend/pyproject.toml` | 后端构建元数据 | `[project]` 段内 `version` |
| 5 | `backend/app/version.py` | 后端运行时事实源 | `__version__` |
| 6 | `.env.example` | 环境变量示例（根） | `APP_VERSION=` |
| 7 | `backend/.env.example` | 环境变量示例（后端） | `APP_VERSION=` |
| 8 | `CHANGELOG.md` | 变更历史条目 | 首个非 Unreleased 的 `## [x.y.z]` |

> `backend/app/version.py` 的 `VERSION_SOURCE_FILES` 与 `scripts/version/version-sources.js`
> 的 `VERSION_SOURCES` **必须逐项同步**。任一侧增删承载点时必须同时改另一侧——
> 这是本决策唯一的强耦合契约。

### 2. 版本号遵循 SemVer 2.0.0，并明确两个正交轴

**轴 A — 平台发布版本**（本 ADR 管辖）：`2.0.0`
表示"整个平台迭代到第几代"，驱动 CHANGELOG、git tag、README badge、运行时 `app_version`。

**轴 B — REST API 契约版本**（`backend/app/api/api_version.py` 管辖）：`v1`
表示"接口协议的第几版"，由 `CURRENT_API_VERSION` 与 `API_MATRIX` 定义，
通过 `X-API-Version` 响应头暴露，驱动向后兼容承诺。

**两轴独立演进，不得混用**：平台 2.x 全程运行 API v1。
实测 `/api/v1/info` 返回 `{"api_version": "1.0.0", "app_version": "2.0.0"}`，两轴并列可见。

破坏性判定规则：

| 变更类型 | 触发轴 A | 触发轴 B |
|:---------|:--------:|:--------:|
| REST 端点删改 / 字段不兼容 | ✅ MAJOR | ✅ 新建契约版本 |
| 数据库不兼容迁移 | ✅ MAJOR | — |
| 新增页面 / Tab / 路由 | ✅ MINOR | — |
| 新增后端端点（向后兼容） | ✅ MINOR | — |
| 缺陷修复 / 无行为变化重构 | ✅ PATCH | — |
| 文档更新 | ✅ PATCH | — |
| 纯客户端 UI 调整（零后端契约变化） | ✅ PATCH | — |

发布候选：`2.1.0-rc.1` → `2.1.0-rc.2` → `2.1.0`（`bump-version.js rc`）。

### 3. 工具化，禁止手工改版本号

| 脚本 | 职责 |
|:-----|:-----|
| `scripts/version/version-sources.js` | 承载点定义 + 解析/写入 + SemVer 运算（零依赖，仅 Node 内置模块） |
| `scripts/version/check-version.js` | 一致性门禁；`--json` 输出供 CI 采集；退出码 0/1/2 |
| `scripts/version/bump-version.js` | `patch` / `minor` / `major` / `rc` 原子化写回 8 处 + 更新 CHANGELOG 骨架 |

根 `package.json` 暴露 npm scripts：`version:check` / `version:check:ci` / `version:bump` / `version:current`。

约定：**bump 脚本不执行 `git commit`**，只打印待执行命令，以便人工审阅完整 diff。

### 4. 后端运行时版本注入链路

```
APP_VERSION 环境变量  ──┐
                       ├─→ Settings.app_version_override > AppInfoConfig.version
backend/app/version.py ─┘        (= app.version.PLATFORM_VERSION)
                                      │
                                      ▼
                     settings.app_version（向后兼容扁平化属性）
                                      │
        ┌──────────────┬──────────────┼──────────────┬─────────────────┐
        ▼              ▼              ▼              ▼                 ▼
   FastAPI app.version  /health       /api/v1/info   OpenAPI 文档     API Docs 中间件
```

修复要点：
- `AppInfoConfig.version` 默认值由硬编码 `"1.0.0"` 改为 `PLATFORM_VERSION`；
- `Settings` 新增 `app_version_override: Optional[str] = Field(alias="APP_VERSION")`，
  使 `.env.example` 中声明的 `APP_VERSION` **真正生效**（此前为死配置）；
  字段命名为 `app_version_override` 以避免与既有 `app_version` 属性重名；
- `app.version` 零依赖、不反向引用配置模块，可安全被导入而不产生循环依赖。

### 5. CI 强制门禁

`.github/workflows/ci-cd.yml` 新增 `version-gate` job：
- 无 `needs`，与 `lint` 并行，秒级返回，尽早暴露漂移；
- 不依赖 `npm ci`（脚本零第三方依赖），Node 版本取工作流既有 `NODE_VERSION`；
- `pull_request` 与 `push` 均触发，失败即阻断。

### 6. 首个正式发布

以 `backend/pyproject.toml` 既有的 `2.0.0` 为锚点（而非另造 2.1.0），
统一全平台至 **`v2.0.0`**，创建首个 annotated tag，并补 `CHANGELOG.md` 与 `LICENSE`。

`1.0.0` 登记为**历史版本（未发布、无 tag）**，仅在 CHANGELOG 谱系表中保留，
不创建对应 tag —— 不为一从未发布的默认值伪造发布记录。

## 后果

### 正面

- **可回滚**：`v2.0.0` 为 annotated tag，后续每个版本均有可审计锚点；
- **口径唯一**：8 个承载点由脚本强制一致，人工漂移被 CI 拦截；
- **运行时可信**：`settings.app_version` 首次返回真实版本；`APP_VERSION` 环境变量从死配置变为可用；
- **版本端点复活**：修复 `_IncludedRouter.path` 缺陷后，`/api` 与 `/api/v1/info` 首次成功注册，
  两轴版本对外可见；
- **零新增依赖**：工具链仅用 Node 内置模块，CI 无需 `npm ci` 即可运行门禁。

### 负面 / 约束

- **强耦合契约**：`VERSION_SOURCE_FILES`（Python）与 `VERSION_SOURCES`（JS）需人工保持同步，
  无自动化校验。缓解：`check-version.js` 启动时若解析不到某个承载点会报「缺失」，
  可间接发现清单错位，但不能发现「新增了承载点却忘了登记」。
- **CHANGELOG 仍需人工填写**：`bump-version.js` 只生成条目骨架与占位提示，
  实际变更明细必须人工对照 `git log` 补全——刻意不做自动 changelog 生成，
  因为本项目 48% 的提交是 `fix`，自动生成会产出无意义噪声。
- **AI 模块版本仍不纳入本体系**：`frontend/src/components/ai/features/CHANGELOG.md`
  的 `8.0.0` 与源码内 `v9.0` 标记是**模块内部代号**，与平台版本正交。
  本次刻意不合并——合并需要重写 AI 模块的 CHANGELOG，风险大于收益。
  待下一次 AI 模块大版本时再决定是否并入。
- **`APP_VERSION` 环境变量覆盖未经生产验证**：本地已验证 `APP_VERSION=9.9.9` 可覆盖成功，
  但部署流水线（Docker / Compose）尚未实际注入该变量，首次生产发布需观察。

### 不纳入本 ADR（明确排除）

- **REST API 契约版本的治理**：`CURRENT_API_VERSION = "1.0.0"` 与 `API_MATRIX` 的 `v1`/`v2`
  键名不完全对齐（`1.0.0` vs `v1`）。这是轴 B 的内部一致性问题，
  改动会影响读取 `X-API-Version` 的下游客户端，**风险高于收益，留待独立 ADR 处理**。
- **小程序包版本号**：微信开发者工具使用 `project.config.json` 的独立版本号体系，
  `miniprogram/package.json` 仅作平台版本镜像，不承担发布语义。
- **自动发布（semantic-release）**：本项目是 Python + TS + 小程序的混合仓库，
  无 npm registry 发布目标，且需要手工审阅 CHANGELOG，
  全自动发布与当前「多次复核」的工程文化冲突，故采用**半自动**（脚本 + 人工 commit）。

## 备选方案（已否决）

- **`semantic-release` 全自动发布**：依赖 commit message 严格合规与 registry 发布，
  本项目为混合语言仓库、无发布目标，且 48% `fix` 提交会产出无意义条目，否决。
- **Changesets**：仅管理 JS/TS 包，无法覆盖 `pyproject.toml` / `.env.example`，
  仍会留下后端版本漂移，否决。
- **独立版本号（前端 / 后端 / 小程序各自迭代）**：引入版本矩阵，
  每次交付都需声明兼容矩阵，对单团队项目成本远高于收益，且当前三端强耦合
  （前端直接消费后端契约），否决。
- **单一 `VERSION` 文件作为唯一事实源**：`pyproject.toml` 与 `package.json` 无法引用外部文件，
  最终仍需脚本同步——不如直接让各格式原生承载版本并由脚本校验，否决。
- **运行时从 `pyproject.toml` 解析版本**：需在应用启动路径引入 TOML 解析依赖，
  且打包后路径不稳定，否决；改用零依赖 `app/version.py` 模块。
- **为 `1.0.0` 补打历史 tag**：为从未发布的默认值伪造发布记录，会污染版本谱系，否决。
