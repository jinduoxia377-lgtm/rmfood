# ADR-011: 架构收敛 — 三层架构（Controller-Service-Repository）

**状态**: ✅ 已接受 (2026-06-30)
**替代**: ADR-001（六边形架构重构，暂停）

## 上下文

项目自 ADR-001 提出六边形架构（Ports & Adapters）以来，一直尝试向该架构迁移。但在实施过程中出现了以下问题：

1. **领域层文件被删除**：`backend/app/domain/entities.py` 和 `domain/ports.py` 已被删除（git status: Deleted）
2. **importlib 反模式**：`services/formula/__init__.py` 被迫使用 `importlib.util.spec_from_file_location` 动态加载服务，这是循环引用 workaround
3. **架构风格混合**：代码中同时存在六边形风格的 adapter 和传统三层风格的 service，导致开发者困惑
4. **迁移未完成**：60% 的迁移进度不足以产生实际收益，反而增加了维护成本

## 决策

**采用清晰的三层架构（Controller-Service-Repository）**，暂停六边形架构迁移。

### 理由

1. **当前代码量**：后端 247+ Python 文件、120-150 个 API 端点，全面迁移六边形架构的成本极高
2. **团队规模**：小规模团队更需要快速迭代而非完美架构
3. **现有代码兼容性**：三层架构与当前 `api/` + `services/` + `models/` 目录结构天然兼容
4. **渐进式演进**：可以在三层架构基础上，对复杂模块（如 AI 服务）局部使用 Ports & Adapters

### 新目录结构

```
backend/app/
├── api/                    # 控制器层（路由、请求解析、响应格式化）
│   ├── v1/                 # API v1 路由
│   └── deps.py             # 依赖注入（DB session、当前用户）
├── services/               # 业务逻辑层
│   ├── formula/            # 配方服务
│   ├── ai/                 # AI 服务
│   └── auth/               # 认证服务
├── models/                 # 数据模型层（ORM）
├── schemas/                # Pydantic 请求/响应模型
├── core/                   # 基础设施（配置、数据库、中间件）
└── infrastructure/         # 外部适配（消息队列、缓存）
```

### 分层原则

| 层 | 职责 | 依赖方向 |
|----|------|---------|
| Controller (api/) | 路由定义、参数验证、响应格式化 | → Service |
| Service (services/) | 业务逻辑、事务管理 | → Model, Schema |
| Model (models/) | ORM 映射、数据访问 | → Schema |
| Schema (schemas/) | 请求/响应数据验证 | 无 |

### 禁止事项

- Controller 不得直接操作数据库（必须通过 Service）
- Service 不得定义 FastAPI 路由
- 模型层不得依赖 Service 层

### 未来演进

当某个模块（如 AI 服务）变得足够复杂时，可以在该模块内部使用 Ports & Adapters 模式，而不影响全局架构。

## 影响

- **积极**：降低学习曲线，减少架构认知负担
- **积极**：消除 importlib 反模式
- **中性**：六边形架构的 ADR-001 标记为"暂停"而非"废弃"，未来仍可启用
- **负向**：部分已写的六边形代码需要重构
