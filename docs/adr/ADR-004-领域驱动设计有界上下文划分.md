# ADR-004: 采用领域驱动设计的有界上下文划分

## 状态
✅ 已接受 (2026-06-05)

## 上下文

当前服务层（90+ 文件 / 13 子目录）采用技术分层而非业务领域分层：
- `ai/`、`ai_models/`、`formula/`、`data_sources/`、`sync/` 等子目录
- 各目录间的边界不清晰，`ai/` 与 `formula/` 存在循环依赖隐患
- 一个业务需求往往涉及跨 3-4 个模块的修改

## 决策

根据 DDD 的有界上下文（Bounded Context）原则，重新划分领域边界：

```
┌─────────────────────────────────────────────────────────────────────┐
│                    RMFOOD 有界上下文地图                              │
│                                                                      │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐              │
│  │ 配方研发上下文│  │ 实验管理上下文 │  │ AI 智能上下文 │              │
│  │ (核心域)      │  │ (支撑域)     │  │ (核心域)      │              │
│  │              │  │              │  │              │              │
│  │ Formula      │  │ Experiment   │  │ LLM Provider  │              │
│  │ Ingredient   │  │ LabEquipment  │  │ NeuralEngine  │              │
│  │ FormulaSpec  │  │ Sample       │  │ Prediction    │              │
│  └──────┬───────┘  └──────┬───────┘  └──────┬───────┘              │
│         │                 │                 │                        │
│  ┌──────▼───────┐  ┌──────▼───────┐  ┌──────▼───────┐              │
│  │ 合规上下文    │  │ 供应链上下文  │  │ 知识图谱     │              │
│  │ (支撑域)      │  │ (通用域)     │  │ (支撑域)      │              │
│  │              │  │              │  │              │              │
│  │ Regulation   │  │ Supplier     │  │ KnowledgeGraph│              │
│  │ Compliance   │  │ Material     │  │ TCMSP         │              │
│  │ Approval     │  │ Inventory    │  │ DFBP          │              │
│  └──────────────┘  └──────────────┘  └──────────────┘              │
│                                                                      │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐              │
│  │ 用户认证      │  │ 组织管理     │  │ 通知协作     │              │
│  │ (通用域)      │  │ (支撑域)     │  │ (通用域)     │              │
│  └──────────────┘  └──────────────┘  └──────────────┘              │
└─────────────────────────────────────────────────────────────────────┘
```

### 领域分类说明

| 领域类型 | 含义 | 策略 |
|:---------|:-----|:-----|
| **核心域** | 核心竞争力，最需要投资 | 自主研发，持续投入资源 |
| **支撑域** | 业务必需但非差异化 | 自研 + 简化方案 |
| **通用域** | 行业通用能力 | 可考虑购买或开源集成 |

### 上下文间通信方式
- **配方研发 ↔ AI 智能**：通过领域事件异步通信
- **配方研发 ↔ 合规**：通过域服务（Domain Service）同步调用
- **实验管理 ↔ 知识图谱**：通过仓储接口（Repository Interface）只读访问
- **所有上下文 ↔ 用户认证**：通过共享内核（Shared Kernel）的 Token 验证

## 后果

### 正面
- 团队可按领域组建（配方团队、AI 团队、合规团队）
- 一个上下文的修改不影响其他上下文
- 新开发者可以快速理解业务边界
- 微服务拆分时有清晰的领域边界依据

### 负面
- 领域间数据一致性需要 Saga 或事件最终一致性
- 跨上下文查询需要聚合（BFF 层或 API Gateway）
- ACID 事务仅限同一上下文内
