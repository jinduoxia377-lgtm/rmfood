# ADR-001: 采用六边形架构重构核心业务层

## 状态
✅ 已接受 (2026-06-05)

## 上下文

当前应用架构采用传统的三层架构（Controller → Service → Model）：
- **Controller**: FastAPI 路由层，处理 HTTP 请求/响应
- **Service**: 业务逻辑层，直接依赖 SQLAlchemy ORM
- **Model**: ORM 模型，与技术栈深度绑定

随着功能增长到 **247 个 Python 文件、52 个路由模块、90+ 服务文件**，层间耦合导致：
1. 修改一个模块往往需要改动多个无关文件
2. 业务逻辑无法脱离数据库独立测试
3. 切换技术栈（如将 PostgreSQL 替换为其他数据库）需要重写大量代码

## 决策

引入**六边形架构（Ports & Adapters）**，将核心业务逻辑与技术实现彻底分离：

```
Inbound Adapters        Core Domain          Outbound Adapters
┌──────────┐          ┌──────────────┐       ┌──────────┐
│ REST API │ ────────→ │ 纯 Python    │ ────→ │ Postgres │
│ GraphQL  │          │ Entity       │       │ Redis    │
│ gRPC     │ ←─────── │ Value Object │ ←──── │ LLM API  │
└──────────┘          │ Aggregate    │       │ VectorDB │
                      │ Domain Event │       └──────────┘
                      └──────────────┘
```

### 关键约束
1. **领域层（domain/）**：纯 Python，零外部依赖。不导入 FastAPI、SQLAlchemy、Pydantic
2. **端口（ports/）**：Python `ABC` 抽象接口，定义契约
3. **适配器（infrastructure/）**：实现端口接口，包含所有技术依赖
4. **应用层（application/）**：编排用例流程，不包含业务规则

### 试点范围
- 首批试点：**配方模块（formula）** 和 **实验模块（experiment）**
- **不在首批**：AI 服务、肽分析等复杂模块（后续逐步迁移）

## 后果

### 正面
- 核心业务逻辑可脱离 FastAPI/DB 独立测试
- 技术栈更换（如从 PostgreSQL 迁移到 MySQL）不影响领域逻辑
- 新开发者可聚焦于领域规则而非技术实现细节
- 领域事件机制为后续事件驱动架构奠定基础

### 负面
- 初期增加约 15-20% 的接口代码量
- 团队需要学习 DDD 与六边形架构概念
- 现有 90+ 服务文件需逐步迁移，过渡期内存在新旧架构共存
- 调试时增加一层间接调用，需熟悉适配器模式

### 缓解措施
- 编写《六边形架构迁移指南》作为团队培训材料
- 新功能默认使用新架构，旧功能按模块逐步重构
- CI 中加入架构约束检查（禁止 domain/ 导入外部包）

## 对标案例
- **Shopify** 的 Monolith 拆分项目通过 DDD 重构使发布频率提升 4x
- **Uber** 的调度系统采用领域事件模式，事件处理吞吐量提升 10x
- **Microsoft** 的 eShopOnContainers 参考架构验证了六边形架构在 .NET 微服务中的可行性
