# RMFOODFP 宣传页 · 区块架构与视觉设计方案

> 配套文档：`docs/宣传页_专业草案思路_v1.md`（策略草案 v1）
> 本文档落地草案中标注的两个"重点增量"区块——**③ 痛点共鸣** 与 **⑤ 研发全链路**，
> 并给出视觉调性、可访问性、资产需求的统一规范。
> **性质**：纯设计方案，不改动任何前端代码；所有配色引用现有 CSS 变量体系，可在现有 `pages/landing/` 架构上增量实现。

## 一、两个新增区块的详细设计方案

### 1.1 区块③「痛点共鸣」

#### 1.1.1 设计意图

现有落地页"功能罗列扎实，但缺痛点钩子"（草案 §二 关键补强）。
本区块要在 Hero/信任数字条建立"我们是谁、有多大"之后，立刻让受众产生"**这说的就是我**"的代入感，
把话题从"平台有什么"切换到"你正被什么卡住"，为后续"证明能解决"铺路。

叙事上属于 **勾住** 阶段的收口 + **证明** 阶段的引子。

#### 1.1.2 配色语义选择

三个痛点分别对应行业三大卡点，映射到现有 `dimensionConfig` 三维语义，保持全页配色系统自洽：

| 痛点卡 | 行业卡点 | 复用 dimension | 主色（已 WCAG AA） | 语义 |
|:------|:--------|:--------------|:------------------|:-----|
| 卡 1 | 配方说不清**依据** | `data`（数据能力） | `var(--color-secondary-700, #1d4ed8)` 靛蓝 | 依据=数据/可追溯 |
| 卡 2 | 过不了**安全合规** | `ai`（智能研发，safety 子项） | `var(--color-primary-700, #047857)` 翡翠绿 | 合规=研发安全 |
| 卡 3 | 走不到**验证与交付** | `team`（企业协作） | `var(--color-warning-700, #b45309)` 琥珀 | 交付/审计=协作治理 |

> 说明：痛点卡的语义是"问题"而非"能力"，但**沿用同一套 dimension 配色**可保证色板统一、
> 且与后文 Features（同色系=解药）形成"问题→解药"的视觉呼应。
> 痛点卡统一使用 dimension 的 `primaryLight` 作图标底、`primary` 作图标与强调色，
> 不引入任何新色值。转折句统一用 `var(--text-primary)` 深色以示"柳暗花明"。

#### 1.1.3 卡片信息层级（4 层）

每个痛点卡自上而下 4 个层级，逐层递进（问题 → 共情 → 转折）：

1. **图标**（视觉锚点）
   8×8 圆角方块，底色 `cfg.primaryLight`，图标色 `cfg.primary`，`1px solid cfg.primaryBorder`，
   与 Features.tsx `FeatureCard` 头部图标规格完全一致（复用 `getFeatureIcon` + lucide 图标）。
2. **痛点标题**（一句话戳中）
   `text-[18px] font-semibold text-neutral-900`，短句、动词驱动，≤ 12 字。
   例："配方说不清为什么这么配"。
3. **共情描述**（展开场景）
   `text-[14px] leading-[1.7] text-[var(--text-secondary)]`，2–3 行，描述研发/企业真实处境。
   克制、不夸大、不点名竞品。
4. **转折句**（钩向解决方案）
   单独一行，前置一个强调标记（如左侧 2px 色条或 "→" 引导符，色 `cfg.primary`），
   `text-[14px] font-medium text-[var(--text-primary)]`。
   例："→ 依据应当可追溯到药材–成分–靶点。"
   这一句是"问题→解药"的桥，色调用 `primary` 而非 muted，暗示"有解"。

#### 1.1.4 布局

- **桌面（lg 及以上）**：3 卡等宽网格 `grid grid-cols-3 gap-5`，容器 `max-w-6xl mx-auto`（与 Features 一致）。
- **平板（480px–lg）**：`grid-cols-2`，第三卡跨列或单独成行（`last:col-span-full` 可选）。
- **移动端（< 480px）**：`grid-cols-1` 单列堆叠，卡片纵向排列，间距 `gap-5`。

#### 1.1.5 交互与动效

- **入场动效**：每张卡外包一层现有 `<Reveal delay="lp-reveal-delay-{1|2|3}">`，
  与 Features 完全同款（复用 `useReveal` + `lp-reveal-delay-*` token），滚动进入视口时淡入上移。
  三卡错峰（delay 1/2/3），形成"依次浮现"的节奏感，呼应"逐个戳中痛点"。
- **hover**：与 FeatureCard 同款——卡片 `border` 从 `var(--border-color)` 过渡到 `cfg.primary`，
  `transition-all duration-200`，`cursor-default`（痛点卡非可点击，不加链接手势）。
  可选：hover 时转折句色条轻微加宽（2px→3px），强化"有解"暗示。
- **尊重系统偏好**：动效全部走现有 `lp-reveal` 体系，天然继承 `prefers-reduced-motion` 处理（若有），不额外发明动画。

#### 1.1.6 DOM 结构草图（文本缩进，非 JSX）

```
section#pain-points  [aria-label="行业痛点共鸣"]  py-16 lg:py-20  bg-neutral-default  border-t
  div.max-w-6xl.mx-auto.px-*
    ├─ Reveal                                    ← 标题区整体淡入
    │   div.max-w-2xl.mb-12
    │     ├─ span.lp-section-tag                 "行业真实痛点"
    │     ├─ h2.lp-h2                            "配方做得出，为什么走不到交付？"
    │     └─ p.lp-body-sm.text-text-muted        一句话共情引导
    │
    └─ div.grid.grid-cols-1.min-[480px]:grid-cols-2.lg:grid-cols-3.gap-5
         ├─ Reveal[delay=1]                      ← 卡 1（data 靛蓝）
         │   div.lp-card-white  [border-hover→cfg.primary]
         │     ├─ div.icon-box (8×8, bg=primaryLight, color=primary)
         │     ├─ h3.title   "配方说不清为什么这么配"
         │     ├─ p.desc     共情描述 2–3 行
         │     └─ div.turn   [色条 + primary] "→ 依据应可追溯到…"
         ├─ Reveal[delay=2]                      ← 卡 2（ai 翡翠绿）
         │   … 同结构
         └─ Reveal[delay=3]                      ← 卡 3（team 琥珀）
             … 同结构
```

#### 1.1.7 状态说明

- 组件为**纯展示 + 局部 hover state**，无全局状态、无数据请求。
- 每卡一个 `useState<boolean> hovered`（与 FeatureCard 一致），或直接用 CSS `:hover` 实现 border 过渡（更简，推荐）。
- 数据来自新数据文件 `data/painPoints.ts`（结构对齐 `features.ts`：id/icon/title/desc/dimension/turn），
  i18n key 挂 `pages.landing.painPoints.*`。
- 无加载/空/错误态（静态内容）。

### 1.2 区块⑤「研发全链路」

#### 1.2.1 设计意图

展示"**端到端**"，而非单点生成（草案 §二）。这是把平台从"AI 配方工具"升级为
"覆盖 配方设计 → 安全合规 → 实验验证 → COA 出具 → 学术报告 的**研发链路**"的关键叙事区块。
对应核心主张"从君臣佐使到可交付的配方证据链"的"证据链"具象化。

#### 1.2.2 信息架构（5 环节横向流程）

5 个环节，每环节 4 个信息要素：**编号 / 图标 / 环节名 / 一句话价值 / 可交付物**。

| # | 环节 | 图标(lucide) | 一句话价值 | 可交付物（chip 展示） | 建议配色维度 |
|:--|:-----|:------------|:----------|:--------------------|:------------|
| 1 | 配方设计 | `FlaskConical` | 君臣佐使 + 网络药理学给出有据初方 | 配方表（克重配比） | `ai` 翡翠绿 |
| 2 | 安全合规 | `Shield` | 61 类阈值 + 106 种禁忌实时拦截 | 合规性报告 | `ai` 翡翠绿 |
| 3 | 实验验证 | `TestTubes` | 理化/稳定性/口感实测回填 | 实验记录 | `data` 靛蓝 |
| 4 | COA 出具 | `FileCheck`（或 `BadgeCheck`） | 批次溯源，质量可交付 | COA 证书 | `data` 靛蓝 |
| 5 | 学术报告 | `FileText` | 成果可发表、可报奖 | 学术报告文档 | `team` 琥珀 |

> 配色按"研发前段（设计+合规）=ai 绿 / 中段（验证+COA）=data 靛蓝 / 后段（成果+协作交付）=team 琥珀"
> 渐进过渡，暗示"从研发走向交付"的推进感，同时严守三色板，不引入新色。

#### 1.2.3 节点呈现

每个节点是一个竖向小卡（宽度均分），自上而下：

1. **编号圆**：节点顶部一个圆形徽章，内含序号 `1–5`，
   底色 `cfg.primary`（700 级深色）、文字白色 `#ffffff`（深底白字对比充足）。
2. **图标**：编号圆下方或圆内叠放 lucide 图标（色 `cfg.primary`，`strokeWidth 1.8`）。
3. **环节名**：`text-[16px] font-semibold text-neutral-900`，≤ 6 字。
4. **一句话价值**：`text-[13px] leading-[1.6] text-[var(--text-secondary)]`，1–2 行。
5. **可交付物 chip**：节点底部一个 pill 标签，`lp-section-tag` 风格，
   `background: cfg.primaryLight; color: cfg.primary; border: 1px solid cfg.primaryBorder`，
   文案前缀 "可交付："（如 "可交付：COA 证书"）——直接呼应"证据链"卖点。

#### 1.2.4 连接线与方向感

- **桌面横向布局**：5 节点 `flex row`，节点之间用**箭头连接线**（lucide `ArrowRight` 或纯 CSS 细线 + 三角）。
  连接线色用中性 `var(--border-color)` 或 `var(--color-neutral-300)`，**不抢节点主色**。
- **方向感强化**：
  - 编号 1→5 递增本身指示方向；
  - 连接线统一右向箭头；
  - 可选：一条贯穿 5 节点底部的细进度线（`cfg` 主色 30% 透明度渐变，绿→蓝→琥珀），
    象征"证据链"贯穿全程——但保持低饱和，避免喧宾夺主。
- **末端收口**：第 5 节点后可接一个淡色 "→ 可交付的配方证据链" 总结标签，回扣核心主张。

#### 1.2.5 移动端降级为纵向

- **< lg 断点**：流程 `flex-col`，节点纵向堆叠。
- **连接线旋转 90°**：箭头由右向变为**下向**（`ArrowDown` 或 CSS 旋转），
  编号仍在节点顶部，方向感由"从上到下"承接。
- **节点卡变全宽**，价值描述可换行更宽松；可交付物 chip 仍置底。
- 移动端隐藏贯穿进度线（避免纵向拉长后视觉混乱），保留节点间下向箭头即可。

#### 1.2.6 入场动效（逐节点 Reveal）

- **逐节点错峰**：每个节点外包 `<Reveal delay="lp-reveal-delay-{n}">`，
  n 按 1→5 递增（复用现有 `lp-reveal-delay-1..5`；若 token 只到 3，按 `(index % 3)+1` 取模，与 Features 一致）。
- 滚动进入视口时，节点**从左（桌面）/从下（移动）依次淡入**，连接线随之"生长"，模拟流程推进。
- 标题区整体一个 `Reveal` 先行。
- 全部走现有 `lp-reveal` 体系，尊重 `prefers-reduced-motion`。

#### 1.2.7 DOM 结构草图（文本缩进，非 JSX）

```
section#pipeline  [aria-label="研发全链路"]  py-16 lg:py-20  bg-neutral-default  border-t
  div.max-w-6xl.mx-auto.px-*
    ├─ Reveal                                    ← 标题区
    │   div.max-w-2xl.mb-12
    │     ├─ span.lp-section-tag                 "研发全链路"
    │     ├─ h2.lp-h2                            "从君臣佐使，到可交付的证据链"
    │     └─ p.lp-body-sm                        五环节端到端说明
    │
    └─ div.flex.flex-col.lg:flex-row.lg:items-stretch   ← 移动纵 / 桌面横
         ├─ Reveal[delay=1]  div.node (ai 绿)
         │   ├─ div.badge (圆, bg=primary, 白字 "1" + FlaskConical)
         │   ├─ h3 "配方设计"
         │   ├─ p.value "君臣佐使 + 网络药理学…"
         │   └─ span.chip[primaryLight/primary] "可交付：配方表"
         ├─ div.connector  [ArrowRight / ArrowDown]      ← 连接线
         ├─ Reveal[delay=2]  div.node (ai 绿)
         │   └─ … "安全合规"  chip "可交付：合规报告"
         ├─ div.connector
         ├─ Reveal[delay=3]  div.node (data 蓝)
         │   └─ … "实验验证"  chip "可交付：实验记录"
         ├─ div.connector
         ├─ Reveal[delay=1]  div.node (data 蓝)
         │   └─ … "COA 出具"  chip "可交付：COA 证书"
         ├─ div.connector
         └─ Reveal[delay=2]  div.node (team 琥珀)
             ├─ … "学术报告"  chip "可交付：学术报告"
             └─ (可选) span "→ 可交付的配方证据链"
```

#### 1.2.8 状态说明

- **纯展示 + 静态数据**，无交互状态、无请求。
- 节点/连接线无 hover 依赖（流程图非操作对象）；如需 hover 强调，仅节点轻微上浮 `translateY(-2px)` + 阴影，不改变数据。
- 数据来自 `data/pipeline.ts`（结构：id/order/icon/name/value/deliverable/dimension），
  i18n key 挂 `pages.landing.pipeline.*`。
- 无加载/空/错误态。
- **响应式状态**：仅一个断点切换 `flex-col`↔`flex-row` 与箭头方向，无 JS 状态，纯 CSS。

## 二、与现有区块的衔接（插入位置与理由）

### 2.1 目标序列（对照草案 §二 14 区块）

草案已给出叙事节奏 **勾住 → 证明 → 拆解 → 消除顾虑 → 行动**。
两个新区块插入后，现有 landing 的渲染顺序调整为：

| 序 | 区块 | 阶段 | 来源 |
|:--|:-----|:-----|:-----|
| 1 | Hero | 勾住 | 复用 |
| 2 | HeroMetricsBar | 勾住 | 复用 |
| **3** | **痛点共鸣** ✨ | **勾住收口** | **新增** |
| 4 | Features（三维核心能力） | 证明 | 复用 |
| **5** | **研发全链路** ✨ | **证明收口** | **新增** |
| 6 | Algorithms | 拆解 | 复用 |
| 7 | DataSources | 拆解 | 复用 |
| 8 | ProductPreview | 拆解（眼见为实） | 复用 |
| 9 | UseCases | 拆解（对号入座） | 复用 |
| 10 | 交付形态（Web/小程序/Docker/API） | 拆解 | 复用/强化 |
| 11 | TrustSignals | 消除顾虑 | 复用 |
| 12 | Pricing | 行动前 | 复用 |
| 13 | FAQ | 消除顾虑 | 复用 |
| 14 | CTABanner + Footer | 行动 | 复用 |

（LaunchCountdown / SocialProof / Navbar 按草案 §六 待拍板项决定去留，不在本文档范围。）

### 2.2 痛点共鸣 → 插在 HeroMetricsBar 之后、Features 之前（第 3 位）

**为什么**：
- 前两位（Hero + 数字条）已建立"我们是谁 + 有多大"，但都是**平台视角**。
- 紧接着放痛点，立刻切换到**用户视角**，完成"勾住"的最后一击——"这说的就是我"。
- 痛点的转折句正好是 Features 三维能力的"问题引子"：痛点卡（问题）→ Features（解药），
  且两者共用同一套 dimension 配色，视觉上"问题与解药同色呼应"，过渡自然。
- 若把痛点放更后（如 Features 之后），就失去"先共情再证明"的钩子作用；放更前（Hero 之前）则还没建立信任就倒苦水，显得负面。第 3 位是节奏最优解。

### 2.3 研发全链路 → 插在 Features 之后、Algorithms 之前（第 5 位）

**为什么**：
- Features 证明"我们**有能力**解决痛点"（单点能力），但仍是**模块化**展示。
- 研发全链路紧接着把这些能力**串成端到端流程**，回答"这些能力如何协同走完从设计到交付"——是"证明"阶段的收口与升华。
- 放在 Algorithms（算法深度）之前合理：先给"全链路鸟瞰"，再用 Algorithms 深入其中"多目标优化"这一环的**技术细节**，符合"先全景后特写"的认知顺序。DataSources 则进一步支撑链路的"数据底座"。
- 这样"证明"阶段形成 **能力点（Features）→ 链路全景（全链路）→ 技术深度（Algorithms）→ 数据底座（DataSources）** 的层层递进，节奏张弛有度。

## 三、视觉调性规范

### 3.1 核心张力：中式底色 × 现代数据可视化

草案 §四 要求"传统智慧 × 现代工程"的视觉张力。落地原则：

- **中式底色**通过**内容与符号**体现，而非新配色：
  - 文案保留"君臣佐使""药食同源""辨证"等术语（如全链路第 1 节点"君臣佐使 + 网络药理学"）；
  - 可选用极淡的中式纹理作区块背景（如宣纸/本草线条纹），但透明度极低（≤ 5%）或直接省略，避免破坏简洁；
  - 区块标签（`lp-section-tag`）文案本身承载中式语义（"研发全链路""君臣佐使"）。
- **现代数据可视化**通过**结构与图形**体现：
  - 全链路的**流程图/连接线/编号节点**=工程感；
  - 复用现有 Features 的**编号列表（lp-numbered）、关键数字（keyMetric）、技术标签**范式；
  - 图标统一 lucide 线性图标（`strokeWidth 1.8`），细线、几何、克制，呼应图谱/Pareto/雷达的"数据可视化"调性。
- **张力来源**：中式**语义**（文案/术语）配现代**形式**（网格/流程/数字/线性图标），二者叠加而非混色，避免"国潮风"过度装饰。

### 3.2 配色 token（严格沿用现有体系）

所有新区块颜色**只**引用 `features.ts` 中 `dimensionConfig` 已用的 CSS 变量，禁止新色值：

| 用途 | token |
|:-----|:------|
| 主强调色（ai 维度） | `var(--color-primary-700, #047857)` |
| 主强调浅底（ai） | `var(--color-success-50, #ecfdf5)` |
| 主强调边框（ai） | `var(--color-success-200, #a7f3d0)` |
| 主强调色（data 维度） | `var(--color-secondary-700, #1d4ed8)` |
| 浅底 / 边框（data） | `var(--color-secondary-50)` / `var(--color-secondary-200)` |
| 主强调色（team 维度） | `var(--color-warning-700, #b45309)` |
| 浅底 / 边框（team） | `var(--color-warning-50)` / `var(--color-warning-200)` |
| 正文主色 | `var(--text-primary)` / `text-neutral-900` |
| 正文次色 | `var(--text-secondary)` |
| 弱化文字 | `var(--text-muted)` |
| 边框 / 连接线 | `var(--border-color)` / `var(--color-neutral-300)` |
| 区块底 | `bg-neutral-default` |

> 推荐做法：新区块**直接 import 现有 `dimensionConfig`**（来自 `data/features.ts`）取色，
> 而非硬编码变量字符串——从源头保证与 Features 同源、同语义、同步演进。

### 3.3 留白与层级原则

- **区块间距**：沿用 `py-16 lg:py-20`（与 Features 一致），区块间 `border-t border-t-neutral-200` 分隔，节奏统一。
- **容器**：`max-w-6xl mx-auto px-[var(--space-apple-md)] sm:px-6 lg:px-8`，全页统一栅格。
- **间距 token**：用现有 `var(--space-apple-sm/md/lg)`，与 Features 的 `p-[var(--space-apple-lg)]`、`gap-5` 对齐，增加呼吸感。
- **层级三段式**（每区块统一）：`section-tag`（小标签，定调）→ `lp-h2`（主标题，定题）→ `lp-body-sm`（引导句，定 scope）→ 内容区。与 Features 标题区结构完全一致。
- **避免堆砌**：痛点 3 卡、链路 5 节点，数量克制；每个信息单元只承载一个核心信息，关键数字/可交付物用 chip/metric 单独强调，正文不堆形容词。

## 四、可访问性与对比度（WCAG AA）

### 4.1 硬约束

草案与现有代码已确立：所有**文本用途的强调色必须用 700 级深色**以满足 WCAG AA 4.5:1。
`dimensionConfig` 注释明确——"primary 用于文本对比（12px 标签 / 14px 标题 / 图标色），需满足 WCAG AA 4.5:1 → 全部改用 700 级深色"。新区块**完全沿用此约定**。

### 4.2 如何保证（逐项落实）

1. **文字强调色只用 700 级**：
   痛点转折句、链路节点价值/可交付物 chip 文字，凡用 dimension 主色，一律取 `cfg.primary`
   = `--color-*-700`（#047857 / #1d4ed8 / #b45309），**绝不**用 400/500 级（对比不足）。
2. **浅底深字**：chip 与图标框用 `primaryLight`（50 级极浅底）+ `primary`（700 级深字/图标），
   浅底深字对比充足，与 Features 现状一致。
3. **编号圆深底白字**：链路编号圆 `bg = cfg.primary(700)`, 文字 `#ffffff`——深色底白字，对比远超 4.5:1。
4. **正文层级**：标题 `text-neutral-900`、描述 `var(--text-secondary)`、弱化 `var(--text-muted)`，
   均为现有已验证 AA 的文字 token，不新造灰阶。
5. **从源头取色**：import `dimensionConfig` 而非散写字符串，杜绝误用浅色；代码评审时只需核对"文本色是否来自 `cfg.primary`/`--text-*`"。
6. **非文本对比**：连接线、边框等非文本图形满足 WCAG 1.4.11 非文本对比（≥ 3:1）——
   `var(--border-color)`/`neutral-300` 在浅底上已满足，主色边框（700 级）更充裕。
7. **语义与键盘**：
   - 区块用语义化 `<section aria-label="...">`；
   - 链路流程若节点含交互（如点击展开），用 `<ol>` 有序列表 + 可聚焦元素，编号 `1–5` 对屏幕阅读器有意义；
   - 痛点卡为纯展示，不放假按钮；
   - 动效走 `lp-reveal`，尊重 `prefers-reduced-motion`（不额外发明动画）。
8. **图标可访问**：装饰性图标加 `aria-hidden="true"`；承载含义的图标配 `aria-label` 或紧邻文字标题。

> 验收口径：上线前对新区块所有文字/背景组合跑一次对比度检测（如 axe / WebAIM），
> 确认全部 ≥ 4.5:1（正文）/ ≥ 3:1（大字与图形）。

## 五、资产需求清单（ProductPreview 真实脱敏界面素材）

对应草案 §六 待补第 3 项。ProductPreview 含 4 个 Tab（对话/图谱/数据/合规），需采集**真实、脱敏**界面素材。

| Tab | 内容 | 尺寸建议 | 格式 | 脱敏要点 |
|:----|:-----|:--------|:-----|:--------|
| **对话** (Chat) | 一轮有代表性的"需求 → 配方建议"对话，展示流式输出与配方结构 | 16:10，≥ 1440×900 逻辑分辨率；导出 @2x | PNG（静帧）或 WebP/MP4（3–6s 动图，展示打字机流式效果） | 隐去真实用户账号/租户名/内部模型代号（对外统一 v2.0.0）；配方数据用公开/示例数据 |
| **图谱** (Graph) | 知识图谱 局部：药材–成分–靶点–疾病 子图展开 | 同上，正方形或 4:3 更适合图状 | PNG / SVG（矢量优先，图谱线条清晰） | 节点标签用公开药材/靶点；隐去内部 Neo4j 主机/查询语句 |
| **数据** (Data) | 数据源面板：四源融合（TCMSP/SymMap/RMCHM/CFAM）+ 活性肽/食品原料 | 16:10 | PNG | 隐去同步任务中的内部路径/密钥/私有端点 |
| **合规** (Compliance) | 安全合规检测报告：61 类阈值命中 + 三级预警 + 合规结论 | 16:10 | PNG | 用示例配方跑出的报告；隐去真实客户/批次号 |

**通用规范**：
- **格式**：静态用 **PNG**（UI 文字锐利，避免 JPEG 压缩糊字）或 **WebP**（体积更小）；
  动图用 **WebP/MP4**（静音、循环、3–6s），避免 GIF（色深低、体积大、字糊）。
- **分辨率**：导出 **@2x**（Retina），逻辑尺寸对齐 ProductPreview 内容区（约 `max-h-[480px]` 内、去掉侧边栏后的宽高比）。
- **深浅色**：ProductPreview 当前为深色窗口（`lp-preview-window` 深色标题栏/侧栏），素材底色应与之协调；
  建议同时备**浅色内容区 + 深色边框**版本，避免深色截图在浅色主题下突兀（视主题支持而定）。
- **统一裁剪**：4 张素材窗口尺寸/圆角/边框一致，仅内容区不同，切换 Tab 时视觉稳定。
- **口径一致**：截图中版本号统一显示 **v2.0.0**，不暴露内部代号（草案 §三 口径纪律）。
