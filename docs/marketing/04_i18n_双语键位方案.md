# 04 · 落地页 i18n 双语键位方案

> 面向：RMFOODFP 落地页「痛点共鸣」「研发全链路」两个新区块 + Hero 升级。
> 范围：**仅设计文档，不改动任何 i18n 资源文件或组件代码。**
> 依据：实际读码 `frontend/src/i18n/**`、`frontend/src/pages/landing/**`、`docs/宣传页_专业草案思路_v1.md`。

## 一、现状盘点

### 1.1 资源文件位置

i18n 采用 **单 `translation` 命名空间 + 模块化语言包深合并** 架构：

| 角色 | 路径 | 说明 |
|:--|:--|:--|
| i18next 初始化 | `frontend/src/i18n.ts` | `initReactI18next`，单 `translation` 命名空间；`lng` 默认 `zh-CN`，`fallbackLng: ['zh-CN','en-US']` |
| 语言包汇总 | `frontend/src/i18n/{zh-CN,en-US,de-DE}/index.ts` | 用 `deepMerge` 把各模块合并进 `translation` |
| **landing 资源（中）** | `frontend/src/i18n/zh-CN/pages/landing.ts` | 默认导出 `{ landing: { cta, pricing, faq } }` |
| **landing 资源（英）** | `frontend/src/i18n/en-US/pages/landing.ts` | 同结构英文值 |
| landing 资源（德） | `frontend/src/i18n/de-DE/pages/landing.ts` | 同结构（本方案不覆盖德语，仅中英） |

> 「105 个 i18n 文件」= 3 语言 × (顶层 4：`ai/common/nav/index`) + 3 语言 × (31 个 `pages/*.ts`)。landing 是 31 个 pages 模块之一。

### 1.2 键的解析路径（关键，决定前缀）

`{lang}/index.ts` 的合并逻辑（三语一致）：

```ts
export default {
  translation: deepMerge(
    { ai },
    common,
    nav,
    { pages: deepMerge({}, dashboard, formula, /* … */, landing) },
  ),
}
```

- `pages/landing.ts` 默认导出 `{ landing: { cta, pricing, faq } }`，被合并进 `pages`；
- 因此 **landing 文案在运行时的真实键树是 `pages.landing.<section>.*`**（例：`pages.landing.pricing.sectionTitle`）。

> ⚠️ **重要发现（键前缀不一致，详见 §5 技术债 T-1）**：现有 landing 三个已接 i18n 的组件（`CTABanner` / `Pricing` / `FAQ`）与两个数据文件（`data/pricing.ts`、`data/faqs.ts`）里写的是 **`landing.*`**（**缺 `pages.` 前缀**）；而全站正常工作的页面（如 `DashboardPage`、`label/*`）统一用 **`pages.<module>.*`**（如 `t('pages.dashboard.welcomeBack')`、`t('pages.labelCheck.title')`）。即 landing 资源挂在 `pages.landing.*`，但取值代码用 `landing.*`，二者不匹配。**新增区块本方案按“正确且可解析”的 `pages.landing.*` 设计**，并同时给出与现有代码一致的降级前缀，交由实现时统一拍板（见 §3.0）。

### 1.3 现有键的组织结构

以 `zh-CN/pages/landing.ts` 为例，层级为 `landing → section → (子组) → 叶子`：

- **section 级元信息**：`ariaLabel` / `sectionLabel` / `sectionTitle` / `sectionSub`（Pricing 还有 `ariaLabel`）。
- **列表型内容用「索引数组 + 固定子键」**（这是本仓库最值得复用的约定）：
  - Pricing：`landing.pricing.plans.<planId>.{name, desc, cta, features.<i>}`，`planId ∈ {free, pro, enterprise}`，`features.<i>` 为数字索引数组（i18next 支持按索引取数组元素）。
  - FAQ：`landing.faq.items.<i>.{q, a}`，`i ∈ [0,8)`。
- **表单/交互型**：`dialogTitle` / `dialogDesc` / `successTitle` / `labelXxx` / `phXxx`（placeholder）/ `errXxx` / `submitting` / `submit` 等扁平叶子键。
- **枚举映射**：`industries.{pharma,supplement,food,research,other}`、`budgets.{lt10,b10to50,b50to100,gt100}`。
- **插值**：`{{email}}`、`{{id}}`（`interpolation.escapeValue: false`，React 安全）。

### 1.4 数据文件与组件的协作范式（i18n 键引用版）

`data/pricing.ts`、`data/faqs.ts` 是**纯键引用**：数据文件只导出**稳定键字符串**，组件用 `t(key)` 取值。

```ts
// data/faqs.ts —— 单一数据源，SEO.tsx 也复用它
const F = 'landing.faq.items';
export const sectionLabelKey = 'landing.faq.sectionLabel';
export const faqs: FAQItem[] = Array.from({ length: 8 }, (_, i) => ({
  qKey: `${F}.${i}.q`, aKey: `${F}.${i}.a`,
}));
```

```tsx
// sections/FAQ.tsx —— 组件只认键
const { t } = useTranslation();
<span>{t(sectionLabelKey)}</span>
{faqs.map((faq, i) => (<AccordionItem key={i}>…{t(faq.qKey)}…{t(faq.aKey)}…</AccordionItem>))}
```

## 二、键位命名规范（从 pricing / faqs 提炼）

| 规则 | 约定 | 现有示例 |
|:--|:--|:--|
| R1 命名空间 | 单 `translation`，landing 全部挂在 `landing.*` 子树下（合并后物理路径 `pages.landing.*`） | `landing.cta.*` / `landing.pricing.*` / `landing.faq.*` |
| R2 区块根 | 每个区块一个 `camelCase` 顶层段 | `cta` / `pricing` / `faq` |
| R3 区块元信息 | 固定四键：`ariaLabel`、`sectionLabel`（小标签）、`sectionTitle`、`sectionSub` | `landing.pricing.sectionTitle` |
| R4 重复条目 | 用**稳定 id 或数字索引 + 固定子键**，不把整段文案塞进一个键 | `plans.pro.name`、`items.3.q` |
| R5 列表顺序键 | 顺序敏感用数字索引 `0,1,2…`；语义稳定用 id（`free/pro/enterprise`） | `features.0`、`plans.pro` |
| R6 语义后缀 | 表单类统一 `labelXxx` / `phXxx`（placeholder）/ `errXxx` / `submit` / `submitting` / `successXxx` / `dialogXxx` | `landing.cta.phEmail`、`errEmail` |
| R7 数据文件 | 只导出 `*Key` 字符串常量与结构，不导出文案；组件 `t(key)` | `sectionLabelKey`、`faqs[].qKey` |
| R8 SEO 单源 | 需进 JSON-LD 的文本，键由 `data/*.ts` 单一来源导出，`SEO.tsx` 用 `i18n.t(key)` 复用 | `SEO.tsx` 遍历 `faqs` 生成 `FAQPage` |
| R9 可扩展 | 新增条目只**追加索引/追加 id**，不改既有键，保证翻译不丢 | `plans` 追加 id、`items` 追加索引 |

> **R10（新增，强烈建议）**：取值前缀在实现时**全局二选一并统一**——(A) 修正为与资源一致的 `pages.landing.*`；(B) 保持现有 `landing.*`。本方案正文按 (A) `pages.landing.*` 编写（正确可解析），§3.0 给出 (B) 的一键替换规则。**同一批次不要混用两种前缀。**

## 四、接入指引

### 4.1 组件内取值（`useTranslation`）

新区块组件遵循现有 `FAQ.tsx` / `Pricing.tsx` 范式：

```tsx
import { useTranslation } from 'react-i18next';
// 数据文件只导出键（沿用 pricing/faqs 的纯键引用范式）
import { sectionLabelKey, sectionTitleKey, sectionSubKey, painItems } from '../data/painPoints';

export default function PainPoints() {
  const { t } = useTranslation();
  return (
    <section id="pain-points" aria-label={t('pages.landing.painPoints.ariaLabel')}>
      <span className="lp-section-tag">{t(sectionLabelKey)}</span>
      <h2 className="lp-h2">{t(sectionTitleKey)}</h2>
      <p className="lp-body-sm">{t(sectionSubKey)}</p>
      {painItems.map((it, i) => (
        <article key={i}>
          <span>{t(it.tagKey)}</span>
          <h3>{t(it.titleKey)}</h3>
          <p>{t(it.descKey)}</p>
        </article>
      ))}
    </section>
  );
}
```

配套 `data/painPoints.ts`（键引用版，遵循 R7）：

```ts
const P = 'pages.landing.painPoints';
export const sectionLabelKey = `${P}.sectionLabel`;
export const sectionTitleKey = `${P}.sectionTitle`;
export const sectionSubKey    = `${P}.sectionSub`;
export const painItems = [
  { tagKey: `${P}.items.0.tag`, titleKey: `${P}.items.0.title`, descKey: `${P}.items.0.desc` },
  { tagKey: `${P}.items.1.tag`, titleKey: `${P}.items.1.title`, descKey: `${P}.items.1.desc` },
  { tagKey: `${P}.items.2.tag`, titleKey: `${P}.items.2.title`, descKey: `${P}.items.2.desc` },
];
```

`pipeline` 同理用 `steps.<i>.{step,title,desc}`，`hero` 为扁平叶子键（`t('pages.landing.hero.titleLine1')`）。

### 4.3 SEO.tsx 纳入新区块（JSON-LD）

`SEO.tsx` 当前用 `i18n.t(key)` 从 `data/faqs.ts` 单源生成 `FAQPage`。新区块纳入结构化数据有两种合理做法：

- **痛点共鸣**：适合用 `@type: 'WebPage'` 的 `about`/`description`，或直接作为 `SoftwareApplication.description` 的补充句，**不建议**每张痛点卡单独做 schema（痛点不是独立实体）。可复用 `t('pages.landing.painPoints.sectionTitle')` + `sectionSub` 拼进软件描述。
- **研发全链路**：天然适合 `@type: 'HowTo'`（`step` 序列），把 `pipeline.steps.<i>` 映射为 `HowToStep`：

```ts
// SEO.tsx 内，仿照 FAQPage 由 data 单源生成
import { pipelineSteps } from './data/pipeline';
const pipelineHowTo = {
  '@type': 'HowTo',
  '@id': 'https://www.rmfood.cn/landing#pipeline',
  name: i18n.t('pages.landing.pipeline.sectionTitle'),
  step: pipelineSteps.map((s, i) => ({
    '@type': 'HowToStep',
    position: i + 1,
    name: i18n.t(s.titleKey),
    text: i18n.t(s.descKey),
  })),
};
// 追加进现有 JSON_LD['@graph'] 数组即可（不要替换整个 graph）
JSON_LD['@graph'].push(pipelineHowTo);
```

**要点**：① 复用 `data/*.ts` 键（R8 单源，保证页面与 schema 文案一致）；② 用 `i18n.t`（`SEO.tsx` 已 `import i18n from '@/i18n'`）；③ 追加进 `@graph`，不破坏既有 `Organization` / `SoftwareApplication` / `WebSite` / `FAQPage`；④ `og:locale` 现为硬编码 `zh_CN`，若做双语 SEO 需按当前 `i18n.language` 动态化（技术债 T-4）。

## 五、风险提示与技术债（只记录，不修改）

### T-1【高优先 · 前缀不一致，疑似失效键】
landing 资源物理路径为 **`pages.landing.*`**（由 `{lang}/index.ts` 合并决定），但已接 i18n 的三个组件与两个数据文件取值用 **`landing.*`**（缺 `pages.`）：
- `sections/CTABanner.tsx`（61 处 `t('landing.cta.*')`）
- `sections/Pricing.tsx`（`t('landing.pricing.*')`，含 `errNameEmail/errEmail/errSubmit/contactSales/dialogTitle/…`）
- `sections/FAQ.tsx`（`t('landing.faq.title')`、`ariaLabel`；`faqs[].qKey/aKey` = `landing.faq.items.*`）
- `data/pricing.ts`（`landing.pricing.plans.*`、`sectionLabel/Title/Sub`）、`data/faqs.ts`（`landing.faq.*`）

对比：`DashboardPage.tsx` 用 `t('pages.dashboard.*')`、`label/*` 用 `t('pages.labelCheck.*')`——全站正常范式是 `pages.<module>.*`。**结论：landing 现有取值前缀很可能解析不到（回落/显示键名），需在实现新区块时一并统一（见 §3.0 二选一）。** 本文因约束“不修改代码”，仅记录，不改。

### T-3【中优先 · SEO 双语缺口】
`SEO.tsx` 的 title / meta / JSON-LD 全量硬编码中文（见 T-2），即使页面文案走 i18n，英文语境下的 SEO 元信息与结构化数据仍是中文，且 `og:locale` 不随语言切换。纳入新区块时应同步考虑动态化。

### T-4【低优先 · 德语资源未覆盖】
本方案仅覆盖 zh/en；`de-DE/pages/landing.ts` 存在但需同步补 `hero/painPoints/pipeline` 三段，否则德语页回落中文（`fallbackLng` 含 `en-US`，实际会回落英文）。
