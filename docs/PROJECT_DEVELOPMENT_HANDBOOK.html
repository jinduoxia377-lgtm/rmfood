4.1 问题诊断 自 ADR-001 提出六边形架构重构以来，实施过程中暴露了以下核心问题： | 问题 | 严重程度 | 代码证据 | |:-----|:--------:|:---------| | `domain/` 层文件被删除 | 🔴 严重 | `entities.py`、`ports.py` 已不在版本控制中 | | `importlib` 反模式 | 🔴 严重 | `services/formula/__init__.py` 使用动态加载规避循环引用 | | 混合架构风格 | 🟡 中等 | 部分服务采用六边形 adapter，部分仍是传统三层 | | 迁移不彻底 | 🟡 中等 | 60% 迁移进度未产生实际收益，反而增加维护成本 | ##

21.2 技术决策（ADR-027） **从自定义组件迁移至 shadcn/ui + Radix UI 的核心原因：** 1. **一致性**：所有组件共享同一设计 Token 体系 2. **可维护性**：Radix UI 提供无样式但功能完善的原始组件 3. **无障碍**：Radix 内置 ARIA 支持，通过 ARIA 合规测试套件 4. **生态兼容**：Tailwind CSS 4.x 原生支持，与项目技术栈无缝集成 5. **TypeScript 安全**：严格的类型定义，消除 `as any` 强制转换 **迁移策略：** - Phase 4 的兼容桥接层确保零运行时破坏 - 旧组件导出路径保持兼容，渐进式替换 - antd → shadcn 迁移指南覆盖剩余 4 个数据库页面 ##
