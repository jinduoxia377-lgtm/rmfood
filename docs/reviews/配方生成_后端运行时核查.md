## 2. 【P0 剂量单位疑点】结论：**不是 bug，是设计如此**（限量数据本身即 12000mg）

### 现象
`/ai/generate` 返回 `herb_combination[].dosage="11.7g"`（茯苓），而 `safety_verdict.warnings` 报：
`'茯苓' 用量 11700.0mg 接近限量 12000mg/天（80%阈值）`。

### 结论
**单位换算正确，限量数据本就如此，非单位/限量错误。**
- 11.7g = 11700mg，换算无误（`compliance_ingredients` 构造处 `dosage_mg = grams * 1000.0`，见 `safety_gate.py:266`）。
- 茯苓的日限量在法规表里**就是 12000mg/天**：`backend/app/services/compliance/formula_compliance.py:38`
  `"茯苓": 12000, ...`（`FOOD_HERB_MAX_DOSAGE`，注释 L22 说明"法规表原始单位为克/日，已 ×1000"）。
- 即限量 12000mg = 12g。茯苓常规日限量确实处于 12g 量级（法规表口径），并非"被错误压低"。因此"11.7g 触发接近限量"反映的是 **GA 把君药剂量推到了目录限量的 97.5%（11700/12000）**，踩到 80% 预警线，而非单位 bug。

### 触发链（代码证据）
1. 茯苓 11.7g 进入 L3 闸门：GA 出口 `check_formula_safety(herb_combo, auto_clamp=True)`（`formula_generation_service.py:514`）。
2. 闸门第 4 关把剂量转 mg 后调 `check_compliance`（`safety_gate.py:259-273`）。
3. `check_compliance` 判 `11700 > 12000*0.8(=9600)` 且 `11700 ≤ 12000`，落入 80% 预警分支：
   `backend/app/services/compliance/formula_compliance.py:222-225`
   ```python
   elif dosage > max_dosage * 0.8:
       warnings.append(f"'{name}' 用量 {dosage}mg 接近限量 {max_dosage}mg/天（80%阈值）")
   ```
4. 该 warning 透传回 `verdict.warnings`（`safety_gate.py:284`）。

**根因定位**：`formula_compliance.py:222-225`（80% 预警）+ `formula_compliance.py:38`（茯苓限量 12000mg）。
行为符合设计意图（临近目录限量即预警），但暴露一个**真实调优隐患（非 bug）**：GA 倾向把君药剂量优化到贴近目录上限，导致几乎每个候选都带 80% 预警 → 见 §3.2，它会连带把 `safety_passed` 压成 false。

## 3. 【P0 评分疑点】结论：`efficacy_score=0.01` 是**真实计算结果**（GA 地板值，映射关键词在 DB 功效索引命中为 0）；`safety_passed=false` 由 warnings 触发，**合理但偏保守**

### 3.1 efficacy_score=0.01 —— 真实结果，非计算 bug，但暴露关键词失配缺陷

**0.01 的来源是 GA 适应度函数里的硬地板值。**
`backend/app/services/ai/algorithms/genetic_formula_optimizer.py:157-171`（`Individual.evaluate`）：
```python
for effect in target_effects:
    score = 0.0
    for hid, dosage in self.genes.items():
        if hid in herbs:
            s = herb.efficacy_scores.get(effect, 0)     # ← 关键词查不到 → 0
            ratio = (dosage - herb.dosage_min) / max(1, herb.dosage_max - herb.dosage_min)
            score += s * (0.5 + 0.5 * ratio)
    eff_scores.append(score / max(1, len(self.genes)))
self.efficacy = (math.prod(max(0.01, s) for s in eff_scores)) ** (1.0 / max(1, len(eff_scores)))
```
当 `target_effects`（GA 收到的是 `tcm_keywords`）在 `herb.efficacy_scores` 里**全部查不到（get→0）**时，每个 effect 分量被 `max(0.01, 0)=0.01` 抬到地板，几何平均仍 = **0.01**。这与实测 `efficacy=0.01` 精确吻合 → **是真实计算结果**，非浮点/映射 bug。

**根因（关键词失配）**：GA 的 `target_effects` 来自 `build_tcm_keywords(target_effects)`（`formula_generation_service.py:617,656,777`），它把前端 label 经 `EFFECT_LABEL_TO_TCM_KEYWORD` 展开（`formula_generation_service.py:34-101`）。例如 `免疫调节 → ["免疫调节","补气","抗炎"]`（L37）。而 `herb.efficacy_scores` 的键来自数据库 `TCMHerb.extra_knowledge.efficacy_scores`（`herb_knowledge_service.py:26,182`；`data_loader.py:280-297`），是**另一套功效词表**。两组词表一旦在 `免疫调节/抗炎` 等键上无交集，所有 `get(effect,0)=0` → efficacy 触地板 0.01。

- **定位**：`genetic_formula_optimizer.py:167`（`get(effect,0)`）+ `:171`（`max(0.01,...)` 地板）+ `formula_generation_service.py:104-116,34-101`（关键词映射与 DB 功效键不同源）。
- **性质**：`efficacy=0.01` 本身**不是 bug**（计算正确），但它**是真实的质量缺陷信号**——说明该功效标签在数据库功效索引里匹配不到药材，GA 实际是"盲选"（功效目标失效，仅靠 synergy/safety 等其它维度排序）。与 `overall_score=0.6143` 不矛盾：overall 是多维加权（`formula_generation_service.py:503-506`，efficacy 仅占 0.30 权重，其余 safety/taste/cost/synergy/stability 仍在贡献），故 efficacy≈0 也能得到 ~0.6 的 overall。
- 建议（未改码）：核对 `EFFECT_LABEL_TO_TCM_KEYWORD` 展开词与 `TCMHerb.efficacy_scores` 实际键的交集；失配的 label（如 `免疫调节/抗炎`）应映射到 DB 真实存在的键。

### 3.2 safety_passed=false 的判定阈值与 warnings 触发是否合理

**判定阈值：`safety_passed` 当且仅当三态裁定 `status == "PASS"`。**
- `safety_gate.py:99-101`：`is_safe_for_display → return self.status == "PASS"`。
- `formula_generation_service.py:521,541`：`safety_passed = verdict.is_safe_for_display`。
- **status 裁决**：`safety_gate.py:295-302`
  ```python
  if has_critical:            status = "REJECTED"
  elif clamped_any or verdict.warnings:   status = "NEEDS_ATTENTION"
  else:                       status = "PASS"
  ```

**因此：任何非空 `warnings`（包括 §2 的 80% 接近限量预警）都会把 status 压成 `NEEDS_ATTENTION` → `safety_passed=false`**，即便 `is_compliant=true`、`violations=[]`。这解释了实测的 `is_compliant=true / violations=0 / warnings=4 / safety_passed=false / status=needs_attention`（safety_score 仍 0.98，因为 warning 仅轻微扣分：`formula_compliance.py:244-245` `warning_penalty=len*0.1`）。

**是否合理**：
- **逻辑自洽、合理**：`safety_passed` 语义是"完全无保留通过(PASS)"，而 warnings 代表"需关注"，用 `is_safe_for_display=仅PASS` 表达"并非完全无忧"是站得住的保守设计（`safety_gate.py:99-101` 注释"前端唯一可信的安全合规展示依据—三态之一，非布尔反推"）。
- **但存在设计张力（非 bug）**：80% 预警（`formula_compliance.py:222`）几乎必然被贴上限的 GA 候选触发（§2），使 `safety_passed` 系统性为 false。前端若把 `safety_passed=false` 渲染成"不安全/红标"，会造成"合规却显示不安全"的观感矛盾。这属于**阈值/展示语义需对齐**的调优项，而非计算错误。

### 3.3 附：hybrid 为何 `safety_passed=true`
`/genetic/hybrid` 的 `safety_passed` 来自 `_safety_passed(ind)`（`genetic.py:771/1359`），基于 GA/NSGA 内部 safety 维度，**不经过 L3 `check_formula_safety` 闸门**，故不受 warnings 影响 → true。与主路径 `/generate` 的 L3 闸门口径不一致（前端展示时需注意两种 safety_passed 语义差异）。

## 4. 附：两个空结果/报错端点的根因定位（只读推断）

### 4.1 `/ai/generate/genetic` 与 `/ai/generate/unified` —— 空结果（200 + 0 候选）
- 两端点执行仅 2.5ms / 2.89ms，`total_generations=0` → GA **在 `_select_herbs` 后即早退**于：
  `genetic_formula_optimizer.py:602-604`
  ```python
  if len(candidates) < 3:
      logger.warning(f"候选药材不足 ({len(candidates)})")
      return [], []
  ```
- 对比主路径 `/ai/generate`（同一 `GeneticFormulaOptimizer`）能出候选，差异在**目标功效词与候选池**：
  - 主路径 `run_ga_generation` 用 `tcm_keywords`（多词展开，`formula_generation_service.py:617`）+ RAG/L1 骨架 `include_herbs` 白名单（`:688-762,779`）扩充候选池。
  - `/generate/genetic` 路由（`genetic.py:746,753-757`）直接把 `req.target_effects`（原始 label，未展开）传给 `optimize`，且 `include_herbs=req.include_herbs`（本次请求为空）。
  - 结果 `_select_herbs` 仅按单个 label 查功效索引 + L0 准入过滤（`:564-604`）后 <3 味 → 返回空。
- **性质**：HTTP 200 但**功能性空转**——前端 `generateGenetic`（`ai.ts:1094-1131`）默认不传 `include_herbs`，故该端点在默认入参下大概率恒空。属真实可用性缺陷（非崩溃）。
- `/unified` 同源（`genetic.py:1145-1262`，内部同样调 GA，`generator=ga_optimizer`），且返回 `message:"…候选方案已按综合适应度排序。"` 与 `total:0` **自相矛盾**（`genetic.py` unified 返回体），属误导性成功文案。

### 4.2 `/ai/generate/multi-objective` —— 稳定 500
- 路由 `genetic.py:1275-1436`：`optimizer = NSGAIIOptimizer(config)` 后**直接同步调** `optimizer.optimize(...)`（`:1335-1341`），无 try/except。
- `NSGAIIOptimizer.__init__` 置 `self.evaluator = None`、`_herb_knowledge_loaded=False`（`algorithm.py:46-47`）。
- `optimize → _optimize_pareto → _run_nsga2_loop`，循环内 `:166` 调 `_try_load_herb_knowledge()`，其走 **NSGA 专属的同步加载路径** `FormulaEvaluator._load_herbs_sync()`（`algorithm.py:104-105`；`evaluator.py:122-144`）。该路径在 `get_herbs()` 不足 20 味或加载异常时 `raise RuntimeError`（`evaluator.py:137-139`）并向上传播（`algorithm.py:116-118`）→ 路由无兜底 → **500**。
- 关键差异：主路径 `/ai/generate` 走 `genetic_formula_optimizer` 的 `_try_load_herb_knowledge`（`genetic_formula_optimizer.py:430-499`），并有 `formula_generation_service.py:626-642` 的"功效索引为空强制重载"自愈；**NSGA 路径无此自愈**。
- **性质**：稳定可复现的服务端错误（已两次实测 500：3596ms / 739ms）。精确抛点需后端 traceback 日志确认（本次无法读取后端 stdout），但代码路径明确指向 `NSGAIIOptimizer` 的 evaluator/herb 加载初始化缺失。**未改码**，建议后端侧复核 `_load_herbs_sync` 抛错并补路由级兜底 + evaluator 初始化。

## 6. 总摘要

- **端点四态**：`/generate`、`/generate/advanced`、`/genetic/hybrid`、`presets` **可用**；`/multi-objective` **稳定 500（报错）**；`/genetic`、`/unified` **200 但恒 0 候选（空结果）**。无硬契约不符（hybrid 的 `name_cn/dosage_g` 形态前端已归一化兼容）。
- **P0 剂量单位**：**非 bug，设计如此**。茯苓限量在法规表即 12000mg/天（`formula_compliance.py:38`），11.7g=11700mg 换算正确（`safety_gate.py:266`），触发的是 80% 接近限量预警（`formula_compliance.py:222-225`）。真实隐患是 GA 把君药推到贴近目录上限。
- **P0 评分**：`efficacy_score=0.01` 是**真实计算结果**（`genetic_formula_optimizer.py:171` 的 `max(0.01,...)` 地板，因关键词在 DB `efficacy_scores` 索引命中为 0，`:167`），非计算 bug，但暴露"功效标签→DB 功效键"失配、GA 功效目标实质失效的质量缺陷。`safety_passed=false` 阈值=仅 `status=="PASS"`（`safety_gate.py:99-101,295-302`），**warnings（含 80% 预警）触发它逻辑自洽、合理但偏保守**，与前述 GA 贴上限行为叠加会造成"合规却显示不安全"的观感。
