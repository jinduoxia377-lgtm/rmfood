## 1. efficacy_score 计算链路与 0.01 的真实含义

### 1.1 关键词展开（两段归一化，最终 4 词）

`backend/app/services/ai/formula_generation_service.py`
- `:34-101` `EFFECT_LABEL_TO_TCM_KEYWORD`：`"增强免疫" → ["免疫调节","补气","抗炎","抗氧化"]`
- `:104-116` `build_tcm_keywords()`：展开 + 去重保序 → `["免疫调节","补气","抗炎","抗氧化"]`
- `:617` `run_ga_generation()` 调 `build_tcm_keywords(target_effects)` 得 `tcm_keywords`，`:656/:776` 作为 `target_effects` 传入 GA。

`backend/app/services/ai/algorithms/genetic_formula_optimizer.py`
- `:546` `optimize()` 内再做一次 `normalize_effect_aliases()`（`herb_knowledge_service.py:90-108`）。对本链 4 词为**幂等**（免疫调节→免疫调节；补气/抗炎/抗氧化不在别名表→原样保留），最终仍是 `["免疫调节","补气","抗炎","抗氧化"]`。

### 1.2 功效评分公式（核心）

`genetic_formula_optimizer.py:157-171`（`Individual.evaluate`）：

```python
for effect in target_effects:              # 4 个关键词
    score = 0.0
    for hid, dosage in self.genes.items(): # 该个体选中的每味药材
        if hid in herbs:
            herb = herbs[hid]
            s = herb.efficacy_scores.get(effect, 0)   # ← 精确键查找，查不到=0
            ratio = (dosage - herb.dosage_min) / max(1, herb.dosage_max - herb.dosage_min)
            score += s * (0.5 + 0.5 * ratio)
    eff_scores.append(score / max(1, len(self.genes)))  # ← 170行：除以「总基因数」稀释
self.efficacy = (math.prod(max(0.01, s) for s in eff_scores)) ** (1.0/len(eff_scores))  # ← 171行：几何平均 + 0.01 硬地板
```

三个决定性特征：
1. **精确键查找**（`:167`）：`herb.efficacy_scores.get(effect, 0)`，键不存在即 0。
2. **除以总基因数稀释**（`:170`）：分母是 `len(self.genes)`（该个体全部药材数，含对该关键词无贡献者），不是「有贡献药材数」。
3. **几何平均 + 0.01 硬地板**（`:171`）：4 个 `eff_score` 各自 `max(0.01, s)` 后取几何平均。

**⇒ `efficacy_score` 四舍五入到 0.0100 的唯一可能**：4 个 `eff_score` **全部被压在 0.01 地板上**（即每个关键词 `score/len(genes) ≤ 0.01`）。只要有任一关键词评分明显高于 0.01，几何平均就会显著大于 0.01（例：`[0.01,0.01,0.01,0.02]→0.0119`）。

`_format_ga_candidates`（`formula_generation_service.py:496`）直接 `efficacy = ind.efficacy`，`:537` `efficacy_score=round(efficacy,4)` 原样透出。

### 1.3 0.01 是真实计算值，但其成因不是词表/数据缺失

- **是真实值**：在线端点复现两次，均稳定返回 `efficacy_score=0.01`（cand: 黄芪/茯苓/白扁豆/党参 与题述 茯苓/大枣/枸杞子/菊花/党参/白扁豆）。
- **不是映射/数据缺失**：见 §2 实查——这些词、这些药材在 DB 都有真实功效分。
- **离线同库同适配器重跑 = 0.24，不是 0.01**：见 §2.3。这说明当前代码 + 当前 DB 数据，正常情况下 `efficacy≈0.24`；只有当 `herb.efficacy_scores` 在评分时为空（所有 `.get` 返回 0）才会 4 项全地板 → 0.01。

### 1.4 根因代码位置

- **地板值来源**：`genetic_formula_optimizer.py:171`（`max(0.01, s)`）——`0.01` 这个数字字面量即此处。
- **触发条件**：`:167` 全部 `.get(effect,0)=0`，即评分所用 `herbs`（`optimizer._herbs`，来自全局单例 `get_global_herb_knowledge()`）中 `efficacy_scores` 为空/未含目标键。
- **数据本应存在**：适配器 `herb_knowledge_adapters.py:199-208` 从 `TCMHerb.extra_knowledge.efficacy_scores` 读入；`:186-192` `herb_id` 解析。
- **已知自愈缺陷**：`formula_generation_service.py:626-642` 试图在「有药材但功效索引为空」时强制重载，但自愈条件是 `not _hk.get_efficacy_to_herbs()`；当索引非空（如被后台预热 `_schedule_async_warmup`，`:174-176` 填充）而**单味药材 `efficacy_scores` 仍为空**时，自愈**不触发**，GA 照样对空功效打分。这是 0.01 在服务进程中稳定复现、而离线新进程正常的最佳解释（进程级状态/时序 bug，而非词表或数据问题）。

## 3. overall_score 加权公式与权重合理性

`formula_generation_service.py:503-506`：

```python
overall = efficacy*0.30 + safety*0.25 + taste*0.10
        + cost*0.15 + synergy*0.10 + stability*0.10
```

- **efficacy 权重 = 0.30**（最大单权重，与 `Individual.DEFAULT_OBJECTIVE_WEIGHTS` `genetic_formula_optimizer.py:112-119` 一致）。
- **为什么 efficacy=0.01 时 overall 仍=0.61**：其余 5 维占 0.70 权重，且来自 GA 内部维度（`ind.safety/taste/cost/synergy/stability`），实测普遍 0.8–0.99。以在线候选拟合：`0.01*0.30=0.003`，剩余 `0.6048/0.70≈0.864` 平均 → overall≈0.61。**算术自洽，归一化正常**。
- **判定：设计如此（非 bug）**。但暴露一个**语义问题**：efficacy 权重最高（0.30），却因 §1 的运行时失效恒为 0.01，导致「最重要的维度实际贡献≈0.003」，GA 的功效优化目标名存实亡，overall 被 safety/taste/cost 主导。修好 §1 后 overall 才有真实功效含义。
- **另一处不一致（值得记录）**：`overall` 里的 `safety` 用的是 **GA 内部维度 `ind.safety`**（`:497`，约 0.9），而对外展示的 `safety_score` 用的是**合规闸门分** `compliance_score=verdict.score/100`（`:522,:535`）。两者口径不同，overall 的 safety 分不等于用户看到的 safety_score。

## 4. safety_passed 判定逻辑（为何 compliant 却 false）

`backend/app/services/ai/safety/safety_gate.py`：

- `:99-101` `is_safe_for_display` ≡ (`status == "PASS"`)。
- `:521`（`formula_generation_service.py`）`safety_passed = verdict.is_safe_for_display`。
- `:295-302` status 裁决：
  ```
  if has_critical:            status = "REJECTED"
  elif clamped_any or warnings: status = "NEEDS_ATTENTION"   # ← 任何 warning 都进来
  else:                        status = "PASS"
  ```

warning 的来源：`formula_compliance.py:222-225`——单味用量 > 目录限量 80% 时追加非阻塞告警「`'X' 用量 …mg 接近限量 …mg/天（80%阈值）`」。GA 把君臣佐使剂量推到目录上限附近（如茯苓 11.7g≈11700mg，限量 12000mg，>80%×12000=9600），**几乎每候选必踩 80% 线** → 必产生 warnings → `status=NEEDS_ATTENTION` → `safety_passed=false`。

**判定：设计如此，但偏严、有误导。**
- 逻辑自洽（`safety_passed` 被严格定义为「零告警的 PASS」）。
- 但对用户误导：`is_compliant=true`、`violations=[]`（无任何真实违规），仅 4 条「接近限量」的**咨询级提示**，却被前端呈现为「不安全」。三态里的 `NEEDS_ATTENTION`（需关注）被二元布尔 `safety_passed=false` 压平成「不安全」，丢失了「合规但需留意剂量」的语义。

## 5. 修复建议方向（**未实施**）

1. **【P0】修「功效数据未送达 GA」的运行时失效**（真正的 0.01 根因）
   - 自愈条件从 `not get_efficacy_to_herbs()` 收紧为「校验目标关键词可命中」：在 `formula_generation_service.py:626-642` 处，对 `tcm_keywords` 逐个检查 `any(h.efficacy_scores.get(kw,0)>0 for h in _hk.get_herbs().values())`，任一关键词全库命中数为 0 或单味候选功效分普遍为空时强制 `load_herbs(force_reload=True)`。
   - 排查 `_schedule_async_warmup`（`ai/__init__.py:174-176`）是否构建了与 `get_herbs()` 内 `efficacy_scores` **脱钩**的索引，或存在启动时序覆盖：确保后台预热不会把已加载好的功效分清空/替换。
   - 增加启动后自检日志：`init_ai_services` 结束时打印「带功效分的药材数 / 总药材数」，若为 0 立即告警。

2. **【P1】修 efficacy 归一化的稀释缺陷**（`genetic_formula_optimizer.py:170`）
   - 分母 `len(self.genes)` 改为「对该关键词有贡献（`s>0`）的药材数」，或改为按**理论最大分**归一（`Σmax(efficacy_scores.values())`），避免「选越多味、单关键词分越被摊薄」的反向激励；同时保留 `:171` 地板但改为更合理的下界（如 0.05）并**仅在真无命中时启用**。

3. **【P1】补齐 28/69 缺失映射词的 DB 功效键**（影响其它功效，不影响增强免疫）
   - 对 `利湿/活血化瘀/降血脂/益气固表/扶正/疏肝理气/…` 等 28 词，要么在 `EFFECT_LABEL_TO_TCM_KEYWORD`/`EFFECT_ALIAS_TO_KEYS` 把它们归一到 DB 真实键（如 利湿→祛湿、降血脂→降脂、活血化瘀→活血），要么在 `tcm_herbs.extra_knowledge.efficacy_scores` 补灌这些功效键。建议优先做**映射归一**（零数据风险）。

4. **【P1】放宽 `safety_passed` 口径 / 透传三态**（`safety_gate.py:299`、`formula_generation_service.py:521`）
   - 把「仅咨询级 warning（80% 阈值）」与「需人工关注的越界」区分：`is_safe_for_display` 可对 `NEEDS_ATTENTION && is_compliant && 无 CRITICAL && 无 clamped` 的纯 advisory 场景返回 true（或新增 `is_compliant_for_display`）；至少把 `status=needs_attention` + warnings 明细透传到前端，替代单一布尔。

5. **【P2】统一 overall 的 safety 口径**
   - `formula_generation_service.py:504` 的 `safety`（GA 内部维度）与对外 `safety_score`（合规闸门分）口径不一，建议 overall 也改用合规分或明确命名区分，避免「overall 里的 safety ≠ 展示的 safety_score」。
