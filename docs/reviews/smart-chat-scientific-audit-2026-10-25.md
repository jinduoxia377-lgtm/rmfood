## 🔴 P0 — 阻塞级问题

### 问题 1：系统提示词仍含「绝对安全」绝对化用语（广告法合规风险）

| 位置 | 内容 |
|------|------|
| `backend/conf/prompts/default.yaml:90` | `1. 【绝对安全】所有建议必须在药食同源目录安全剂量范围内` |
| `backend/app/services/ai/orchestration/chat_engine.py:43` | `1. 【绝对安全】所有建议必须在药食同源目录安全剂量范围内` |

**现象：** 两处系统提示词均使用"绝对安全"作为核心原则标题。

**科学/合规影响：**
- 中国《广告法》第九条明令禁止在健康食品/功能性食品宣传中使用"绝对"等绝对化用语
- 医学/营养学领域不存在"绝对安全"的物质——部分人群存在过敏、特异体质或药物相互作用风险
- 该表述一旦对外发布，构成实质性法律合规风险

**建议：**
- 将「绝对安全」改为「**安全优先（严格遵守目录规范）**」
- 补充「任何建议在出现不适时应立即停用并咨询医师」的兜底声明

---

### 问题 2：主对话路径（chat.py）无输出安全检查

| 位置 | 现象 |
|------|------|
| `backend/app/api/ai_modules/chat.py:454-481` | 非流式路径：直接返回 `llm.chat()` 结果，无安全过滤 |
| `backend/app/api/ai_modules/chat.py:704-710` | 流式路径：直接 yield `llm.chat_stream()` 内容，无安全过滤 |

**现象：** 项目内已存在完整的安全输出过滤体系：
- `backend/app/services/ai/safety/output_filter.py` → `check_output()`
- `react_chain.py:150` → 已调用 `check_output(full_answer)`
- `agent/orchestrator.py:288` → 已调用 `check_output(raw_answer)`

但主对话路径（`/chat` 和 `/chat/stream`）**从未调用** `check_output()`，LLM 原始输出直接返回给用户。

**科学影响：**
- LLM 可能输出不含专业依据的剂量建议（如"每日XXg黄芪"），无任何后端校验
- 无法拦截幻觉性文献引用（虚构 DOI、不存在的临床研究）
- 无法识别或拦截不当的医疗建议（如"可替代处方药"）
- 与 agent 工作流有安全覆盖、主对话路径裸漏的不一致架构

**建议：**
在主对话路径的 LLM 调用完成后、返回前端前，统一调用 `check_output()`：
```python
# chat.py:481（非流式）
from ...services.ai.safety import check_output
output_result = check_output(answer)
if not output_result.is_safe:
    logger.warning("[Chat] 输出被安全过滤: %s", output_result.risk_level)
    # 注入免责声明或截断敏感内容
answer = output_result.sanitized_text
```
流式路径同理，在最后一个 content chunk 后追加安全标记事件。

### 问题 3：配方剂量无运行时后端校验

| 路径 | 现状 |
|------|------|
| `/chat` 主路径 | LLM 自由输出剂量文本，无任何后端数值校验 |
| `/chat/stream` 主路径 | 同上 |
| `/ai/formula/validate` | 存在剂量校验，但仅在后端保存时触发 |

**现象：** 
- 主对话路径中，LLM 可自由输出任意剂量（如"人参 50g/天"，远超安全上限 3g）
- 仅当用户点击"保存到配方库"时，才触发 `/ai/formula/validate` 的后验校验
- 校验失败时仅提示用户，不阻止对话本身

**科学影响：**
- 用户可直接在对话中看到明显超剂量的配方建议，且无即时警告
- 剂量校验是处方级安全措施，不应仅在"保存"时触发
- 对于高敏感用户（慢性病患者），对话中的超剂量建议可能产生直接误导

**建议：**
- 在主对话路径中增加**轻量级剂量预校验**：提取 LLM 输出中的剂量数值，与 `_BUILTIN_HERBS` 的 `dosage_max` 对比，超标时在回复末尾追加红色警示 Callout
- 或将 `check_output()` 集成到主路径，使其同时具备剂量合规检查能力

## 🟡 P1 — 严重问题

### 问题 4：药食同源目录数量过时（110 → 114）

| 位置 | 当前值 | 正确值 |
|------|--------|--------|
| `chat_engine.py:30,35` | "2023版110种" | "2023版114种" |
| `default.yaml:academician`（未核查，需确认） | 待确认 | 114 |

**背景：** 2023年12月国家卫健委发布公告，新增红枣[干]、人参（5年及以下）、党参、山药4种物质正式纳入药食同源目录，总数由110种升至**114种**。

**科学影响：** 提示词中写死过时数据，导致 LLM 引用错误数量，影响专业可信度。

**建议：** 将两处"110种"统一更新为"114种"，并同步核查 YAML 配置。

---

### 问题 5：提示词强制字数要求诱发 LLM 注水

| 位置 | 内容 |
|------|------|
| `chat_engine.py:91` | `每条回答不少于1000字` |
| `default.yaml:academician` | 未硬性规定字数（但 `min_response_length=800` 仍触发扩展调用） |

**现象：** 硬性字数要求导致 LLM 对简单问题（如"黄芪的功效是什么"）也会展开至1000字以上，大量输出冗余内容。

**科学影响：** 
- 信息密度降低，专业内容被稀释
- 模型为凑字数可能重复解释或输出常识性废话
- 与 YAML 中"JSON 卡即最终交付，不再展开长篇 Markdown"的设计意图相矛盾

**建议：** 删除硬性字数要求，改为"回答应充分覆盖问题相关维度，不简单重复常识"。对简单问题允许简短回答（≥200字）。

---

### 问题 6：`严禁写「适量」` 强制精确但缺乏毒性校验

| 位置 | 内容 |
|------|------|
| `default.yaml:64` | `用量必须精确到克（如 10g、6-12g），严禁写「适量」` |

**现象：** 提示词要求 LLM 输出精确克数，但主对话路径**无任何后端剂量上限制约**。两者结合意味着：
1. LLM 会自信地输出精确剂量（如"人参 9g"）
2. 这些剂量可能超出实际安全上限
3. 用户看到的是一条"精确但可能危险"的建议

**科学影响：** "精确"不等于"安全"。强制精确但无校验，反而比模糊表述更具误导性和风险。

**建议：** 在输出中增加条件约束："若无法确定安全剂量，请明确标注『需遵医嘱，建议咨询专业医师』"，而非盲目输出具体数值。

---

### 问题 7：`【严禁】禁止输出旧格式` 的强制指令压制不确定性表达

| 位置 | 内容 |
|------|------|
| `default.yaml:69` | `【严禁】禁止输出旧格式配方 JSON...必须严格使用上面的 "blocks" 结构` |

**现象：** 提示词中多处使用"严禁"（共 3 处），同时要求"必须全部覆盖""精确到克"，形成高度强制性的指令框架。这与同一文件第 93 行的"循证克制"原则（"证据不足时明确标注『需进一步验证』"）存在内在冲突。

**科学影响：** 强力格式指令压制了模型表达不确定性的空间，可能导致：
- 对证据不足的配方也输出确定性评分
- 模型为避免违反指令而"编造"具体剂量

**建议：** 将"严禁"替换为"建议优先使用 blocks 结构"，并明确允许在信息不足时使用占位符（如"剂量待定，需进一步咨询"）。

### 问题 8：贝叶斯优化器与主对话路径完全脱钩

| 组件 | 状态 |
|------|------|
| `bayesian_formula_optimizer.py` | 独立模块，提供配方设计方案 |
| `chat_engine.py` | 在主路径中未被调用（见 P0-5 架构说明注释） |
| `/chat` 主路径 | 直接使用 LLM，不触发贝叶斯优化 |

**现象：** 主对话路径的"配方设计"请求完全依赖 LLM 自由生成，无算法辅助。而 `bayesian_formula_optimizer.py` 拥有完整的药食同源参数数据库（含 `dosage_min`/`dosage_max`/`safety_index`），但从未被主路径消费。

**科学影响：**
- LLM 自由生成的配方缺乏算法层面的安全性保障
- 贝叶斯优化器已具备剂量合规校验能力，但因架构隔离无法在主路径生效
- 用户感受到的"专业配方设计"实际上是纯 LLM 输出，质量波动大

**建议：** 在 `chat.py` 主路径中，当检测到配方类问题时，异步调用 `get_chat_engine().chat()` 而非直接调用 LLM，让引擎的三级降级、质量检查、贝叶斯优化真正生效。

## 🟢 P2 — 建议改进

### 问题 9：缺少强制免责声明

**现象：** 所有系统提示词中，虽有"辅助定位"（YAML:93）和"不能替代医师诊断与治疗"（chat_engine.py:56 的注释提及），但**没有在任何输出模板中强制要求 LLM 在每条回答末尾添加免责声明**。

**建议：** 在 `_build_system_prompt()` 的输出要求部分，追加：
```
最后必须附：> ⚠️ 本建议仅供参考，不能替代专业医师诊断与治疗。使用前请咨询医师。
```

### 问题 10：结构化输出 schema 缺少剂量单位校验

**现象：** `default.yaml` 的 blocks schema 中 `dosage` 字段类型为字符串（如"10"），无单位约束（g/kg/mg 混用风险），前端 `parseDosage()` 通过正则 `\d+(?:\.\d+)?` 提取，不处理单位转换。

**建议：** 在 schema 中明确 dosage 单位为"g"，并在 `parseDosage()` 中增加单位校验。

### 问题 11：辨证分析（dialectics）路径无 RAG 增强

**现象：** `chat.py:698-701` 调用 `analyze_dialectics(req.question)` 时未传入 `db` 参数，无法使用平台知识库增强辨证准确性。

**建议：** 将 `db` 传入辨证分析函数，支持基于用户知识库的个性化辨证。

### 问题 12：多轮历史截断无 Token 级估算

**现象：** `chat.py:454-459` 使用 `req.history[-10:]` 截断，固定取最近10条，未考虑消息实际长度。单条消息可达 3000 字符（chat_engine.py:198），10条最多 30000 字符，可能超出多数模型上下文窗口。

**建议：** 改用 Token 级估算（按字符数/4近似），确保总长度在模型窗口内。

## 附录：安全架构现状

```
Agent 工作流（react_chain / agent/orchestrator）
    └── check_output() ✅ 已覆盖

主对话路径（/chat, /chat/stream）
    └── LLM → 直接返回 ❌ 无安全检查
    └── 剂量无校验 ❌ 无后端约束

配方保存路径（/ai/formula/validate）
    └── validate_formula() ✅ 有后验校验

公式引擎（AcademicianChatEngine）
    └── 主路径未接入 ❌ 死代码
```

**核心问题：** 三层架构中，最高频使用的"主对话路径"安全覆盖最薄弱，与 agent 工作流的安全标准不一致。
