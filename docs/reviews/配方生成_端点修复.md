## 一、缺陷现象（修复前，认证会话实测 :8000）

| 端点 | 入参 | 修复前实测 |
|------|------|-----------|
| `POST /ai/generate/multi-objective` | `target_effects:["增强免疫"]` | **HTTP 500**（~350-700ms） |
| `POST /ai/generate/genetic` | `target_effects:["增强免疫"]` | HTTP 200，但 `candidates:[]`、`total_generations:0`、~25ms 早退 |
| `POST /ai/generate/unified` | `target_effects:["增强免疫"]` | HTTP 200，`candidates:[]`、`total:0`，却返回 `message:"…候选方案已按综合适应度排序。"`（自相矛盾） |

用原生 TCM 词 `免疫调节` 直测同样失败（MO 仍 500；unified 仍空且 2ms 早退）。

## 二、根因（运行时 + 源码双确认）

### 缺陷 1：multi-objective 稳定 500
- 路由 `genetic.py` 原 `generate_multi_objective` 直接 `NSGAIIOptimizer(config).optimize()`，**无 try/except**。
- NSGA 路径在 `optimize()` 内部走 `_try_load_herb_knowledge()` → `FormulaEvaluator._load_herbs_sync()`（`evaluator.py:122-144`）；药材不足/服务未就绪时直接 `raise RuntimeError` → 路由无兜底 → 500。
- 主路径 `/ai/generate` 之所以正常，是 `formula_generation_service.py:626-668` 有「功效索引空强制重载」自愈，NSGA 路径没有。

### 缺陷 2：genetic / unified 恒空结果
- GA 内部 `_select_herbs` 按目标功效查 `_efficacy_index`；候选 `<3` 味时 `genetic_formula_optimizer.py:602-604` 早退 `return [],[]`（**不抛异常**）。
- 原先 `genetic` 把前端原始 label（如「增强免疫」）**未展开**就传给 optimize；unified 虽已用 `build_tcm_keywords` 展开，但在 async 请求上下文里 `HerbKnowledgeService` 功效数据未送达 GA（`_efficacy_index` 空）→ 同样早退。
- 主路径正常，因为先用 `build_tcm_keywords()` 把 label 展开为多个 TCM 关键词（「增强免疫」→ `["免疫调节","补气","抗炎","抗氧化"]`），再配合 RAG 白名单扩充候选池 + 功效索引自愈。

### 缺陷 3：unified 误导文案
- GA 空结果（`[],[]`）不抛异常，原代码落到 success 路径，产出 `total:0` 却 `message:"…已排序"`。

### 引擎健康性对照（关键证据）
在进程内串行初始化 `init_ai_services()` 后直接调 GA 引擎（绕开 async 请求时序）：
- `_efficacy_index` 命中数：`免疫调节=11`、`补气=13`、`抗炎=11`、`抗氧化=9`；
- L0 准入过滤后候选 20-21 味（远高于 `<3` 阈值）；
- `optimizer.optimize()` 返回 `candidates=5, history=15`。

**结论：GA 算法内核健康，端点失败是「功效数据未送达 GA」的时序/兜底问题，而非算法缺陷。** 故修复放在路由侧做防御 + 自愈，不碰算法内核。

## 三、修复内容（均在 genetic.py 内）

新增/修改函数：

1. **`_assure_herb_knowledge(tcm_keywords)`（新增，async）** — GA/MO 路由前置自愈闸。
   - 读取全局 `HerbKnowledgeService`，检测「服务缺失 / 药材<20 / 带功效分药材=0 / 目标关键词全库零命中」，命中则 `await load_herbs(force_reload=True)` 强制重载一次并复检。
   - 与主路径 `formula_generation_service.py:626-668` 同源判据；只读/重载服务，不改算法文件。
   - 返回 `True/False` 供调用方决定是否 degraded。

2. **`_build_mo_degraded_response(req, objectives, mode, reason)`（新增）** — 构造 MO 降级响应（HTTP 200 + `degraded:true` + `fallback_reason` 的空候选结构），杜绝 500；诚实返回空候选，绝不伪造。

3. **`generate_genetic`（修改）**
   - `build_tcm_keywords(req.target_effects)` 展开前端 label 为 TCM 关键词（对「已是 TCM 词」的入参原样保留，兼容）；
   - 调用前置自愈 `_assure_herb_knowledge(tcm_keywords)`；
   - `optimize()` 包 `try/except`：异常时 `logger.error` 原始异常 + 返回 `degraded:true` + `fallback_reason` 的空候选结构（HTTP 200），不再 500。

4. **`generate_multi_objective`（修改）**
   - `build_tcm_keywords(req.target_effects or ["免疫调节"])` 展开；
   - 前置自愈 `_assure_herb_knowledge(mo_keywords)`；
   - `optimize()` 包 `try/except`：异常时降级返回 `_build_mo_degraded_response(...)`（HTTP 200），`logger.error` 记原始异常，保证不 500。

5. **`generate_unified`（修改）**
   - 保留原有 `build_tcm_keywords` 展开；新增前置自愈 `_assure_herb_knowledge(tcm_keywords)`；
   - 新增**空结果拦截**：GA 成功返回但 `candidates` 为空时（`([],[])` 不抛异常的场景），回退 `run_ga_generation` 规则引擎兜底，返回 `degraded:true` + 诚实文案「候选不足，未能生成配方，请调整目标功效或约束。」，不再出现 `total:0` 配「已排序」的矛盾文案。

6. **附带健壮性修复（`generate_multi_objective` 持久化段）**
   - `algorithm_params.objective_weights` 原先直接 `req.objective_weights`（`MultiObjectiveRequest` 无此字段）→ `AttributeError`。虽被 `_save_ga_run` 内部 try/except 吞掉，但会丢失落库字段。改 `getattr(req, "objective_weights", None)`，与同处 `seed`/`constraints` 的防御口径一致。

所有修复均加充分中文注释说明根因，遵守「诚实>好看」：绝不伪造候选，宁可如实返回空 + 原因。
