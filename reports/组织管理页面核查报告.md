## 〇、复核查出的严重问题（已修复）

### 问题：组织卡片存储/API 用量显示严重错误
- **现象**：组织列表卡片显示 `存储: 0.0GB / 1073741824.0GB`、`API: NaNK / NaNK`（NaN）。
- **根因**：`OrganizationsPage` 的 `OrganizationContent` 在传给 `OrganizationList` 前，把已换算为**字节**的 `storageUsed/storageLimit` 再次乘以 `1024³`（导致存储上限变成 `1024⁶`），且把 `apiUsage/apiLimit` 字段改名为 `apiCalls`（卡片读取 `apiUsage` 得到 `undefined` → NaN）。
- **影响**：所有组织卡片/表格/紧凑视图的存储与 API 用量全部显示错误；`DataExportDialog` 同样被错误放大。
- **修复**：`OrganizationContent` 直接传递已映射的组织对象（`organizations`）与 `selectedIds`（`Set<number>`），不再二次换算；`DataExportDialog` 的存储字段改为直接传字节值（对话框内部按 `1024³` 显示 GB）。
- **验证**：修复后卡片显示 `存储: 0.0GB / 1.0GB`、`API: 0.0K / 10K`；批量面板（修改权限/导出数据）在单选时正常出现；`tsc --noEmit` 通过。

## 〇·一、权限矩阵深度核查（严重问题已修复）

### 权限矩阵此前存在的问题（用户反馈）
1. **数据模型不匹配**：后端 `GET /permissions` 返回 `{ permissions: { member_management, team_management, formula_access, experiment_access, data_export, api_access } }`，前端却按"角色×资源×动作"矩阵解析 `result.roles[]` → 矩阵永远空白。
2. **保存格式错误**：前端把**数组** `[{resourceId, actions}]` 发送给 `PUT /permissions`（后端期望 `Dict[str, bool]`）→ 保存必然失败（422）。
3. **无限循环请求**：`useToast()` 每次渲染返回新对象，`PermissionMatrix` 的 `load` 依赖 `toast` 导致 `useEffect` 每次渲染都重新拉取 `/permissions`（实测一次操作触发 13 次请求），组件永远停在 loading。

### 修复方案
- **重写 `PermissionMatrix.tsx`**：与后端真实模型对齐，渲染 6 个组织级权限开关卡片（成员管理/团队管理/配方访问/实验访问/数据导出/API 访问），点击卡片切换，保存时提交 `Dict[str, bool]`。
- **修复无限循环**：用 `useRef` 固定 `toast` 引用，`load` 仅依赖 `organizationId`，`useEffect` 只执行一次。
- **更新 `PermissionMatrixData` 接口**（`useOrganizations.ts`）与后端响应一致。

### 实测结果（Playwright）
- 权限矩阵区渲染 + 6 个权限项全部显示：**PASS**；
- 初始状态从后端加载（配方访问=已开启）：**PASS**；
- 点击"配方访问"卡片 → 保存 → 后端 `formula_access=false`：**PASS**；
- 刷新页面后状态保持"已关闭"（持久化）：**PASS**；
- `tsc --noEmit` 通过。

### A. 本次深度核查新发现并已修复的缺陷

### B. 仍存在的严重设计缺陷
#### 1. 自定义角色是"假配置"（创建后不生效）
- **现象**：设置页可创建自定义角色（名称+权限集），保存后仅在 `settings.custom_roles` 中存储；
- **根因**：后端没有任何业务逻辑消费自定义角色——成员权限判断仍只按系统角色（owner/admin/member/viewer），自定义角色**不参与任何实际权限控制**；
- **本质**：与当初权限矩阵"保存不生效"同类，但自定义角色需要"成员↔角色"关联模型（现有 `organization_members` 只有单一 `role` 字段），无法简单接入；
- **建议**：① 移除/下线自定义角色编辑器（避免误导）；② 或扩展成员模型支持多自定义角色分配（较大工程）。

#### 2. 角色命名不一致（Editor vs member）
- **现象**：自定义角色编辑器（`PermissionManager`）系统角色为 Owner / Admin /**Editor** / Viewer；而组织成员角色下拉是 owner / admin /**member** / viewer；
- **影响**：两处角色枚举不一致（Editor ≠ member），用户容易困惑，且自定义角色体系与实际成员体系无法对应。

#### 3. 权限矩阵与自定义角色两套体系冗余
- 设置页同时存在"权限矩阵"（组织级 6 开关）与"自定义角色"（RBAC 角色编辑器），语义重叠且互不关联，存在产品设计冲突。

### C. 本次深度核查确认正常的功能
- 详情页状态显示、概览/成员/团队/资源/设置/集成各 Tab、权限矩阵（保存生效+角色感知）、审计日志、批量导出（真实调用接口）、归档/恢复流程、`/organizations/trashed`、组织卡片计数与存储显示。

### D. 结论
- **已修复**：详情状态、回收站；

## 〇·三十、深度核查准确性：活跃率假数据修复

### 问题（严重）：数据概览"活跃率"恒为 100%
- **现象**：将组织某成员**停用（suspend）**后，数据概览仍显示"3 人活跃 / 100%"（真实应为 67%）；
- **根因**：`mapMemberResponse` 中 `status: raw.status || 'active'`，而后端成员接口返回的是 **`is_active`（boolean）而非 `status`** → `raw.status` 恒为 undefined → 停用成员也被标记为 active → 活跃率永远 100%（假数据）；
- **修复**：`status: raw.status || (raw.is_active === false ? 'suspended' : 'active')`；
- **验证**：停用 1/3 成员后，概览正确显示"**2 人活跃 / 67%**" ✅；`tsc --noEmit` 通过。
